# Handoff: code map

This is a map of the current repo for someone picking it up. Other notes cover the rest:

- Product behavior: `notes/SPEC.md`.
- Tables: `notes/SCHEMA.md`.
- Background work: `notes/AGENT_RUNTIME.md`.

- Google setup: `notes/GOOGLE_CALENDAR_SETUP.md`.
- Going live with real families: `notes/PRODUCTION.md`.
- The original voice concierge brief (historical): `notes/brief.md`.

Sunny is a memory-care agent for seniors with MCI or early dementia who live alone, and for the family who coordinate their care. Every surface works from one shared state. Caregivers schedule the day, and the senior confirms on whatever is closest: the home display, the phone or voice. Anything left unconfirmed escalates to family, and a daily digest closes the loop. The agent is a tool, not a companion.

### Phone timeline

The home screen widget and the Live Activity do not run code while they are on screen. iOS asks a widget for a timeline of dated entries and shows each entry at its date, often for hours and often offline. `GET /device/timeline` (`deviceApi.ts`, built by `lib/phoneTimeline.ts`) gives them the server's cards for every instant of the next 24 hours. The Swift code shows those cards and does not implement the rules for what is due. It takes a Bearer device token and has the same gate, `Cache-Control: no-store`, `ETag` and `If-None-Match` 304 as `GET /device/state`. Its requests count toward the same 120 a minute per device as the other device routes.

```
{
  "version": string,       the ETag, see below
  "generatedAt": number,   epoch ms
  "timezone": string,      the household's IANA zone
  "until": number,         generatedAt + 24 hours
  "entries": [ { "at": number, "cards": PhoneCard[] } ]
}

PhoneCard =
  | { "kind": "task",
      "instanceId": string,
      "step": number,             0-based step this card confirms; 0 for a task without steps
      "stepCount": number,        1 for a task without steps
      "stepText": string | null,  the step's text; null for a task without steps
      "label": string,            the task's displayLabel
      "sentence": string | null,  the task's screenSentence
      "detail": string | null,    the task's pillDescription
      "icon": string,             the task type's icon: "pills" (medication), "calendar" (appointment),
                                  "checklist", "bell" (reminder) or "clock" (routine)
      "startsAt": number,         epoch ms of the instance's scheduled time
      "endsAt": number }          epoch ms when its window closes
  | { "kind": "clear",
      "allDone": boolean,
      "next": { "label": string, "startsAt": number } | null }
```

Entries are in ascending order of `at`, and the first `at` is `generatedAt`. An entry holds from its `at` until the next entry's `at`; the last one holds until `until`. Two entries in a row never have the same cards. The client should fetch again before `until`.

`cards` is the queue of what the phone's Done button would act on at that instant, in order:

- Each task instance that is due at that instant adds one task card for each step it has left: its current step first, then the steps after it. The instances come in the order the Done rule picks them (`lib/deviceState.ts` `doneTarget`: the first due task in day order, with tasks carried over from yesterday first).
- The list always ends with exactly one clear card. It describes the screen once every card before it has been confirmed. `allDone` comes from the Now card's rule (`nowCard`) applied to that situation, so it is false while a task is still open, while an event today has not started, and on a day with a missed task. `next` is the next open timed task or event by the `nextItem` rule, counting no task as Now, with its label and start time; it is null when there is none.
- Only due tasks get task cards. A task inside its early-confirm hour gets no task card, so the widget offers no early Done; the clear card can name it as `next`. Anytime tasks never get a task card. A snoozed due task still does.

The client shows the first task card that it has not pressed since the fetch, and the clear card when none is left. A press sends `POST /device/confirm` with that card's `instanceId` and `step`, `pressedAgoMs` and `via: "widget"` or `"live_activity"`. The answers, checked by test (`deviceApi.test.ts`, "POST /device/confirm from the widget"):

- `advanced` on a step that is not the last; `confirmed` on the last step and on a task without steps.
- A second press of the same card changes nothing. It answers `advanced` when the task has already left that step and `confirmed` when the task is already done.
- A widget press up to 60 minutes before the window opens is confirmed (`EARLY_CONFIRM_MS`). A press made earlier than that is refused with "This task is not due yet". The 5-minute limit for `button` presses does not apply to the widget.

`version` is FNV-1a 64 over canonical JSON of the timezone, the first entry's cards and all the later entries. It leaves out `generatedAt`, `until` and the first entry's `at`, which only move with the clock. Two fetches get the same version when the same cards show now and every later change is the same, so polling an unchanged day gets 304. After a 304 the client keeps the `until` it already has.

#### How the cards are computed

Stored instance states change only when the scheduler tick runs, so `lib/phoneTimeline.ts` projects them to each instant and then runs the existing rules (`doneTarget`, `isDue`, `nowCard`, `pickNext`) on the projected day:

- `stateAt` applies the tick's transitions. An open instance is missed from its `windowEnd`, and an upcoming one is due from its `windowStart`. A due instance stays due when the ladder would make it escalated, because every rule the cards use treats due and escalated alike.
- `dayAt` builds the day for the instant's local date: yesterday's instances that are still due (carried over, by `lib/today.ts` `shownOn`), that date's instances, the early-confirm flag at that instant, and that date's events.
- The projection applies at `generatedAt` as well. In the minute before a tick runs, the first entry can therefore be one tick ahead of `GET /device/state`.

The cards can change only at the instants that `changeInstants` lists: each instance's window start, its window end and the start of its early hour; each local midnight; each event's start; and each change of the zone's UTC offset. The rules compare local clock times as text, so a midnight or an event start is listed once for each UTC offset in the 24 hours. That covers a time that occurs twice when clocks go back. A time skipped when clocks go forward is covered by the offset change itself. An event's end is not listed, because it only dims the event's row. The unit tests (`lib/phoneTimeline.test.ts`) check for each case that the cards computed directly at every minute of the 24 hours equal the entry covering that minute. A convex-test in `deviceApi.test.ts` runs the scheduler a minute before and at each change and checks that the device state and a new fetch agree with the prediction.

#### How far ahead it can see

The timeline reads the instances that `GET /device/state` reads: yesterday's that are still due, today's and tomorrow's (`lib/deviceState.ts` `loadDeviceDay`, shared by both routes). The scheduler creates today's and tomorrow's instances on every tick, once a minute, and when a task is saved. Tomorrow's instances therefore exist all day, except between local midnight and the first tick after it. The 24 hours stay inside today and tomorrow except in two cases: a fetch made before that first tick, and a fetch in the last hour before midnight on the eve of a 23-hour day (clocks going forward). In those cases the end of the 24 hours reaches a day whose instances do not exist yet, and the timeline shows no task of that day. It never makes up instances.

### Live Activity

The phone's Lock Screen shows each due task as a Live Activity with a Done button. Only the server starts one, by push. The server also updates and ends it by push, except that the phone ends its own activity after a Done press on it. This section is the contract the Swift code is written against. The Swift code is not built yet.

Code: `lib/liveActivity.ts` (what the Lock Screen should show for an instance, the phases of an activity, the start plan, the merge of the phone's report), `lib/liveActivitySync.ts` (reactions to instance and task changes, the tick's sweep, the proof check, cleanup when a phone is revoked), `liveActivity.ts` (the update and end sender), `phonePush.ts` (`PUT /device/push-state`, widget refresh sender), `lib/widgetRefresh.ts` (the refresh throttle), `lib/apnsPayload.ts` (every APNs body and header), `lib/delivery.ts` and `delivery.ts` (the cue's route). Tables: `liveActivities` and `phonePush` (`notes/SCHEMA.md`).

#### The phone's report

`PUT /device/push-state` takes a Bearer device token and has the same gate, rate limit and `Cache-Control: no-store` as the other device routes. Only a `senior_phone` may call it. A home display gets 403. The body is a JSON object with up to three sections. A section that is present replaces what the server holds for it. A section that is absent changes nothing. Any other key, a token that is not 64 to 200 hex characters, or more than 8 activities gets 400.

```
{
  "liveActivityStart": { "token": hex | null, "enabled": boolean },
  "activities": [ { "key": string, "token": hex | null, "state": "active" | "stale" | "ended" | "dismissed" } ],
  "widgetPush": { "token": hex | null }
}
```

- `liveActivityStart` is the push-to-start token and whether Live Activities are enabled for the app. A `null` token or `enabled: false` clears the stored token.
- `activities` lists every Sunny activity on the phone. `key` is the `activityKey` from the start push. `token` is that activity's update token, or `null` while the phone has none.
- `widgetPush` is the WidgetKit push token. `null` clears it.

A start token or a widget token that another device row holds moves to the phone that reports it. The row that held it loses it, in any household, so one token is never on two rows (`notes/SCHEMA.md`, `phonePush`).

The answer is 200 with one directive for each listed activity that is on the phone (`active` or `stale`) and does not show what it should:

```
{ "activities": [
    { "key": string, "directive": "update", "content": ContentState, "staleAt": number }
  | { "key": string, "directive": "end", "content": ContentState | null }
] }
```

The phone applies each directive to the activity with that key. `staleAt` is epoch ms. An `end` with `content: null` is for a key the server does not know, for example an activity left from an earlier pairing. The phone ends it with the content it has. A second entry for an activity that the same report already listed gets no directive.

The phone sends the whole report, read from ActivityKit each time, at every process launch of a paired phone, on every token or enablement change, when it returns to the foreground, after a Done press and when a background refresh push arrives. It keeps no queue for this. Any report, even `{}`, clears the phone's blind mark (below).

What the phone must do that the server cannot check:

- Keep one activity per `activityKey`. A start push that APNs answered late is sent again with the same key, so the phone can receive two starts for one key. It ends the extra one.
- End every Sunny activity when the device API answers 401. The device was removed or its token revoked, and the server can no longer reach an activity that has no update token.
- After a Done press on the last step, end its own activity with the receipt and dismiss it `receiptMs` later. The server's end push for that press carries the same dismissal time ("The pushes", End). Whether iOS applies it to an activity the app has already ended is a real-phone check.

#### The pushes

Every Live Activity push has `apns-push-type: liveactivity`, topic `<bundle id>.push-type.liveactivity` and priority 10. The frequent-updates Info.plist key stays off. `timestamp` is in seconds and grows by at least 1 with every push to one activity ("Phases of an activity" below).

Start (`aps`):

```
"timestamp": seconds, "event": "start",
"attributes-type": "SunnyTaskAttributes",
"attributes": { "activityKey": string, "instanceId": string, "receiptMs": 10000, "timeZone": string },
"content-state": ContentState,
"alert": { "title", "body", "sound": "default" },
"stale-date": seconds, "relevance-score": number
```

- `activityKey` is the id of the activity's `liveActivities` row. `receiptMs` is how long the phone shows the receipt after a Done press. `timeZone` is the household's IANA zone, in which the phone shows every time on the activity.
- `alert` holds the prompt's own title and spoken sentence, so the start and the notification say the same words. A start for a task that came back after an undo or a reopen has no `sound` key. `startAlert` in `lib/apnsPayload.ts` is the one place that decides this. The alert body is cut until the payload fits 4,096 bytes.
- `stale-date` is the window end, or 7 hours 50 minutes after the start if that is sooner (`ACTIVITY_CAP_MS`). The push expires at the same instant, so a phone that comes back online later does not get an activity that is already stale.
- `relevance-score` is 4,000,000,000 minus the window start in seconds. An earlier task ranks higher.
- There is no `input-push-token` key. The floor is iOS 17.2, and the update token comes from the phone's report.

Update: `"timestamp"`, `"event": "update"`, `"content-state"`, `"stale-date"`. It expires at the stale date.

End: `"timestamp"`, `"event": "end"`, `"content-state"`, `"dismissal-date"`. The dismissal date is the second the start was accepted, which is always in the past, so the banner leaves at once. There is one exception. When the task was confirmed with `via: "live_activity"` by the phone that shows this activity, the dismissal date is the confirm time plus `receiptMs`, so the push does not cut the receipt short (`receiptUntil` in `lib/liveActivity.ts`). A confirm from any other surface, another phone's activity included, dismisses at once. The push expires 12 hours after the start was accepted (`ACTIVITY_LIFETIME_MS`), which is how long iOS can keep an activity.

`ContentState` is `{ card, nextSteps, closed }`:

- `card` is the task card of `GET /device/timeline` without `kind`: `instanceId`, `step`, `stepCount`, `stepText`, `label`, `sentence`, `detail`, `icon`, `startsAt`, `endsAt`.
- `nextSteps` holds the texts of the steps after `card.step`, so the phone can show the next step after a press without the server. It is cut from the end until the content is at most 3,000 bytes (`CONTENT_MAX_BYTES`).
- `closed` is `null` while the task is due, or `{ "kind": "done" | "over", "at": number }`. `done` carries the time the task was confirmed. `over` means the window closed, the task was deleted, the 7 hour 50 minute cap passed or the phone was revoked.

Times inside the content are epoch milliseconds as numbers, and no field is a date type, because iOS decodes push content with default strategies only. Swift should decode `ContentState` with a plain `JSONDecoder()`.

`lib/liveActivityGoldens/` holds one file per push, as `{ "headers", "payload" }`. The compact JSON of `payload` is the body on the wire, byte for byte, and `lib/liveActivityGoldens.test.ts` checks both. The Swift tests decode these files. To change a payload, edit the builder and run `LIVE_ACTIVITY_GOLDENS=update npx vitest run convex/lib/liveActivityGoldens.test.ts`.

| File | Push |
| --- | --- |
| `start.json` | Start for a one-step medication, with sound |
| `start-quiet-steps.json` | Start without sound for a three-step task that came back |
| `update-step.json` | Update after the first step was pressed elsewhere |
| `end-done.json` | End after the task was confirmed on another surface |
| `end-done-receipt.json` | End after Done was pressed on this activity; the dismissal date is 10 seconds after the confirm |

#### The due cue

The due cue is still one `senior_prompt` outbox row per device. Its route is decided when it is delivered (`lib/delivery.ts` `deviceRoute`, `lib/liveActivity.ts` `planStart`). It is a start push when all of these hold, and the time-sensitive notification otherwise:

- the device is a senior phone with a device token, a stored start token, and no blind mark;
- the instance is due or escalated, timed, and inside its window;
- no `liveActivities` row exists yet for this phone and instance, in any phase;
- the phone has fewer than three open activities (`MAX_OPEN_ACTIVITIES`).

The row settles once, with channel `live_activity` or `apns`, so one cue never alerts twice from the outbox. The reprompt 15 minutes later finds the activity's row and is a notification. A banner that the senior swiped away is not started again for that task.

A start that APNs refuses falls back to the notification in the same delivery run. A 410 also deletes the start token. Any other permanent answer keeps it. A retryable failure is retried by the delivery pool with the same activity row and key, and when the retries run out the row is queued once more and routes to the notification (`fallbackAfterPushGaveUp`).

A retryable failure can also be a lost answer to a start that reached the phone. When the phone's report lists a `starting` activity, in any state, the report settles that activity's cue as `sent` on channel `live_activity` (`settleCueAsShown` in `lib/liveActivity.ts`). The retry then finds the cue settled and sends nothing, and the notification does not go out. If the retries ran out before the phone reported, the notification has gone out and the row is `ended` (`start_failed`). A later report that lists that activity as `active` or `stale` makes the row `started` or `live` again, so the phone keeps an activity whose Done works and the server can update and end it.

Proof check. APNs accepting a start does not prove the phone showed it, for example when Live Activities were turned off after the last report. When a start is accepted, `markStarted` schedules `liveActivity.checkProof` 45 seconds later (`PROOF_WAIT_MS`). Proof is the phone's report naming the activity's key, with or without an update token. If the activity is still unproven at the check, the phone is marked blind (`phonePush.blindSince`), and if the instance is still due, one more `senior_prompt` row is queued for that phone, which routes to the notification. A blind phone gets notifications only, and no new Live Activity, until its next report. A phone whose app was force-quit therefore gets the activity's alert and, 45 seconds later, the notification. The product owner accepted that so that a due task is never silent. A check that runs twice does nothing the second time. An unproven start that was quiet, the silent return of a task after an undo or a reopen (`liveActivities.quiet`), marks the phone blind and queues no notification, because the task's cue already went out once.

A task that goes from done back to due or escalated (senior undo, caregiver reopen) after its prompt has fired gets one `senior_reshow` outbox row for each senior phone that can take a start at that moment (`canShowAgain`, the same conditions as the due cue's start, except that ended activities for the task do not count). A phone without a start token, a blind phone, a phone with three open activities and a phone that still has an open activity for the task get no row. The row's route is a start with a silent alert and no fallback. If the phone can no longer take the start when the row is delivered, the row is skipped (`no_live_activity`). When the phone's activity was still open at the reopen because its end push was on the way, `liveActivity.settle` queues the row once that end is accepted. A task reopened before its prompt fired gets nothing here. The ladder's own prompt opens it.

#### Phases of an activity

There is one `liveActivities` row per activity, in one of four phases. In the table, the view is what `activityView` returns for the row's instance at that moment: either the content the Lock Screen should show, or that the activity should end and why.

| From | Event | To | Effect |
| --- | --- | --- | --- |
| no row | A cue routes to a start (`delivery.begin`) | `starting` | Start push |
| `starting` | APNs accepts (`delivery.record`) | `started`, proof `awaited` | Cue row `sent` with channel `live_activity`; proof check in 45 s |
| `starting` | The cue row settles any other way, or is gone | `ended` (`start_failed`, or `instance_gone` when the instance was deleted) | The notification, when the cue had one to fall back to |
| `starting` | The phone reports the key before APNs answered, or after an answer that was lost | `started` (proof `proven`) or `live`; `ended` when the phone reports it `ended` or `dismissed` | Cue row `sent` with channel `live_activity`, so a retry of the start or its fallback sends nothing more |
| `started` | The phone reports the key with an update token | `live` | Update or end push at once if the phone is behind |
| `started` | The phone reports the key without a token | `started`, proof `proven`; `ended` when the view says end | Directive in the reply if the phone is behind |
| `started` | 45 s pass with no report | `started`, proof `missed`; `ended` when the view says end | Phone marked blind; notification if still due and the start was not quiet |
| `started`, proof `proven` or `missed` | The view says end. Checked when the instance changes or is deleted, in a report, after the proof check, when an update token is dropped, and by the tick sweep | `ended` (the view's reason) | A background push that wakes the app when the reason is `confirmed` or `instance_gone` (below). None at the window end or at 7 h 50 min, because the stale date already removed Done |
| `live` | The view's content differs from `shown` | `live` | Update push; `shown` is set when APNs accepts |
| `live` | The instance no longer wants an activity | `ended` (`confirmed`, `window_closed`, `instance_gone`, `expired` or `device_revoked`) when APNs accepts | End push |
| `live` | APNs answers 410, or refuses the push for good for a reason about the token or this payload (`BadDeviceToken`, `DeviceTokenNotForTopic`, `MissingDeviceToken`, `PayloadEmpty`, `PayloadTooLarge`) | `started`, proof `proven`, and then the row above | Update token dropped. The phone's next report can bring a token again |
| `live` | APNs refuses the push for good for any other reason, for example a 403 about the provider token (`ExpiredProviderToken`, `InvalidProviderToken`, `MissingProviderToken`) or a 400 about the request's headers | `live` | Update token kept, because the answer says nothing about it and would come for every token during a key or configuration fault (`refusedThisToken` in `lib/apnsPayload.ts`). The tick sweep queues the push again each minute |
| `live` | APNs fails in a way worth retrying and the delivery pool's retries run out | `live` | The tick sweep queues the push again each minute |
| `live` | 12 hours after the start, still not ended | `ended` | None. iOS has removed it |
| open | The phone reports it `ended` or `dismissed`, or leaves it out of `activities` more than 60 s after the start | `ended` (the view's reason, else `ended_on_phone`) | None |
| `ended` (`start_failed`) | The phone lists it as `active` or `stale` | `started` (proof `proven`) or `live` | The row is counted as started at the report. Directive or push if the phone is behind |
| `ended`, any other reason | The phone still lists it | `ended` | `end` directive in the reply |

`shown` is the content the phone last accepted. Update and end pushes are never stored. `liveActivity.plan` computes the push from the instance when it is sent (`activityView`, then `nextCommand`), so a push that runs twice sends the same thing or nothing. Two jobs that run at the same moment can both send the same push. The phone shows one result.

The server relies on iOS showing the push with the largest `timestamp` and not showing one that arrives later with a smaller timestamp. The field is whole seconds, and two pushes sent in the same second can arrive in either order. `plan` is therefore a mutation: it gives each push of an activity the timestamp `max(now in seconds, the activity's last timestamp + 1)` and stores it in `liveActivities.pushTimestamp` (`nextPushTimestamp`). The start push sets the first value. A burst of pushes runs the timestamp a few seconds ahead of the clock. `liveActivity.settle` writes `shown` only for the update that carries the row's newest timestamp, because an older update that is answered late is not what the phone shows.

Who asks for a push: `changeInstance` and `deleteInstances` (`instanceChanged`, `instanceGone`), a task edit that changes the label, screen sentence, pill description or steps (`taskTextChanged`), a report that brings an update token to an activity that is behind, and the tick's sweep. `instanceChanged` does nothing for the scheduler's own changes, because the tick calls `sweepLiveActivities` at the end of the same mutation. The sweep also queues again, each minute, a push whose retries ran out, and deletes ended rows 7 days after they ended.

An activity without an update token cannot be pushed to. Its row ends on the server as soon as its view says end (`endTokenlessIfOver` in `lib/liveActivitySync.ts`), so it stops counting toward the three open activities and the phone's next report gets the `end` directive. A row whose proof is still awaited is left for the proof check, which marks the phone blind first. When the task was confirmed elsewhere or deleted, the phone would go on showing Done for it, so the server sends that phone a background push to its alert token (`phonePush.wakeToReport`), and the app reports when it wakes. A WidgetKit push runs no app code, so a phone with a widget token gets this push too. It is not held back by the 10-minute widget refresh gap. That gap protects the refresh budget for a widget that is only out of date, and this push goes out once for each activity that ends this way. It is skipped in three cases: the end was found in the phone's own report, the change was a press on that phone's Live Activity or in its app (`via: "live_activity"` or `"phone_app"`, which change the activity on the phone and report after the press), or a background refresh was sent to the phone in the same mutation. A press on the phone's widget is not one of them: the widget's intent runs in the extension, cannot change an activity and sends no report, so that phone is woken like any other.

Removing a device or revoking its device token deletes its `phonePush` row and ends its open activities (`device_revoked`): a live one by push, the others without one.

A paired device can revoke its own device token. `deviceApi.revokeOwnToken` is a mutation without arguments that the device calls with its Clerk session. It takes no device id and clears the token hash of the caller's own device row, so a caregiver or another device cannot use it on someone else's device. A caller that is not a paired device gets `forbidden`. It runs the same steps as `households.revokeDeviceToken` (`revokeTokenOf` in `deviceApi.ts`): the `phonePush` row is deleted, the open activities end, and an audit row `revoke_device_token` is written with the device as the actor. The device stays paired. The app calls it in `runUnpair` (`src/backend/pairing.ts`) after the queued presses are sent and the widget is cleared, and before it signs out, because signing out alone would leave a device token that still works on the server. A device may call it 10 times an hour (`tokenRevokes`).

#### Widget refresh

A widget cannot be told to reload on iOS 17.2 to 25, so after a confirm on another surface it can show a done task as due until its next reload. The server asks for a reload when the day changes in a way the widget's timeline could not predict: an instance changes state or step, a task is added, edited or deleted, a calendar event is added, edited or cancelled (the clear card's `next` can name an event), or the household's timezone changes, by anyone but the scheduler. An event edit that changes no field asks for none. The phone whose own press made the change is not sent one, because a press reloads its widgets anyway.

A phone that reported a `widgetPush` token gets a WidgetKit push (`apns-push-type: widgets`, topic `<bundle id>.push-type.widgets`, body `{"aps":{"content-changed":true}}`). Any other phone that has reported at least once gets a background push to its alert token (`apns-push-type: background`, priority 5, body `{"aps":{"content-available":1}}`), and the app reloads the timelines when it wakes. A phone that never reported gets nothing. The same background push is what wakes a phone whose activity without an update token has ended ("Phases of an activity"). Both pushes have expiration 0, so APNs does not store them. APNs keeps one stored notification per app and device, and a stored refresh could replace a stored prompt.

At most one refresh goes to a phone per 10 minutes (`WIDGET_REFRESH_GAP_MS`, state in `phonePush.widgetRefresh`). The first change sends at once. Later changes inside the 10 minutes are folded into one send when the 10 minutes end. Both mechanisms are best effort. Apple says background pushes are throttled above two or three an hour and are dropped for a force-quit app, and that WidgetKit pushes are budgeted.

#### Platform facts: checked in the documentation, and still to check on a phone

Checked in Apple's documentation on 2026-11-19: the `liveactivity`, `widgets` and `background` push types with their topics and priorities; the `aps` keys above; that a start needs an `alert`; that content is decoded with default strategies; the 4 KB limit; 8 hours active plus up to 4 more on the Lock Screen; that a push-started activity wakes the app, which then receives the update token; that `input-push-token` is for iOS 18; the APNs error reasons ("Handling notification responses from APNs"), of which only `BadDeviceToken`, `DeviceTokenNotForTopic`, `MissingDeviceToken`, the 410 reasons `Unregistered` and `ExpiredToken`, `PayloadEmpty` and `PayloadTooLarge` are about the device token or the payload, while every 403 reason is about the provider's certificate or token.

Not verified, to check on a phone before the pilot:

- that `stale-date` and `dismissal-date` are in seconds (Apple's example suggests it, the text does not say it);
- whether a start alert without `sound` is silent;
- whether an end push whose dismissal date is the end of the receipt leaves the phone's own receipt up until then;
- whether a retried start with the same `activityKey` shows a second activity;
- that iOS does not show an update or end whose `timestamp` is smaller than one it has already applied, and that it accepts a `timestamp` a few seconds ahead of its clock;
- that a background push wakes the app often enough for the report that ends an activity without an update token (Apple says background pushes are throttled and are dropped for a force-quit app);
- what happens to a start on a force-quit phone, and whether the Done intent launches the app there;
- whether APNs stores two starts for one offline phone, or only the last;
- whether the update token arrives on iOS 18 and later without `input-push-token`;
- whether the start alert breaks through Silent mode and Focus as the time-sensitive notification does;
- the priority a WidgetKit push needs (Apple's sample sends none, so the builder uses 10), and the iOS version that first accepts it;
- how long the report takes after a push start, which decides whether 45 seconds is the right proof wait.

### Display frames

The e-ink display only shows what the server draws. `GET /device/frame?page=now|today&format=png|packed` (`deviceFrame.ts`) takes a Bearer device token and has the same gate, rate limit and `Cache-Control: no-store` as the other device routes. It draws the token's own device state (`deviceFrame.frameSourceByToken`) for the screen that the same device reported with `PUT /device/info`.

Until the device reports a screen, frames are 960 x 680 with 4 greys. The route can draw sizes from 478 x 334 to 2048 x 2048 with 2 to 256 greys, and answers anything else with 400. Below 478 x 334, the smallest text would be under 12 pixels. `PUT /device/info` still accepts 1 to 10000 pixels a side, so a device that reports an undrawable screen learns it only from the frame route. How to handle that is an open question.

The pages, and how long each one stays on screen, are the state's `tuning.carousel` (`lib/deviceState.ts` `deviceTuning`, the one place they are kept).

The ETag hashes the page's model (only what is drawn), the screen, the format and `FRAME_RENDERER_VERSION`. A matching `If-None-Match` gets a 304 before anything is drawn. Polling an unchanged screen therefore costs the gate's admit mutation and one query, and no drawing. `lib/frameGoldens/MANIFEST.json` and its test fail when a golden or the font data changes without a `FRAME_RENDERER_VERSION` bump, so a device never keeps an old picture under a matching ETag.

Done contract (firmware): every 200 and 304 response carries two headers. `Sunny-Done-Instance` is the task instance that a Done press acts on while that frame is on screen. `Sunny-Done-Step` is the 0-based step that the frame shows ("0" for a task without steps). The instance is the due Now task, snoozed or not. It is never a task inside its early hour, because the frames draw such a task as upcoming. Both headers are absent when Done acts on nothing.

On a Done press, the firmware sends `POST /device/confirm` with exactly the id and the step of the frame on screen (`step` from `Sunny-Done-Step`), `pressedAgoMs` (how long ago the press happened) and `via: "button"`. When that frame had no instance, the firmware sends nothing. On a step that is not the last, the answer is `advanced`, and the next frame shows the next step. On the last step the answer is `confirmed`. A press that names a step the task has already left changes nothing and answers `advanced` with the current state. That covers a double press before the panel repaints, and a replay whose first POST landed.

The server also refuses an early press: it refuses a `button` press on a task of the household that was not due yet when pressed, with "This task is not due yet". Not due yet means a task that is not done yet, pressed more than 5 minutes before its window opened. The server judges by the press time, so a queued press that is replayed after the task came due is refused too. The 5 minutes (`BUTTON_EARLY_GRACE_MS`) allow for a device clock that drifted while asleep, because refusing a real press leaves a taken dose open and alerts the family. The refusal is audited and budgeted like the device API's other refusals. The phone's surfaces (`widget`, `live_activity`, `phone_app`) keep their early hour. The device must report `pressedAgoMs` to within that 5-minute grace. It should correct its clock from the server when it reconnects, before it replays queued presses.

The design is the iPad's (`sunny_app/src/display/DisplayParts.tsx`, `theme.ts`). Every size is the design's points times `min(width / 1194, height / 834)`. Some rules differ from the device state:

- A task in its early hour (`now.task.early`) is drawn as upcoming: a clear card, a plain row, and Next up taken from the state's `nextUpAfterDue`.
- A snoozed Now task's row is tagged "Later".
- An event that is over is dimmed (the state marks it `past`).

Frames draw the state's current step (`now.task.step`), so a step change changes the ETag and repaints the panel.

Words that the fonts cannot draw are never silently dropped from a dose. `lib/frameText.ts` `cleanText` writes out "µg" as "mcg", and writes out comparison signs, arrows, fractions and similar characters. It drops only the accents of letters that the font lacks. A label left with nothing drawable is drawn as the item's type ("Medication", "Event", "Step 2"). In tests on generated cards at six sizes, the Now card's text never reaches the prompts rule or leaves the card.

Rendering is pure (no clock) and byte-for-byte deterministic; to keep it that way, the renderer uses only `+ - * /`, `Math.floor` and `Math.sqrt`. Frames are not cached, because in Node a 960 x 680 frame draws in about 15 ms and encodes in under 20 ms. At 2048 x 2048 x 256, encoding adds about 22 MB of memory for a real frame (44 MB for noise).

To change a screen:

1. Edit `lib/frame.ts`.
2. Run `FRAME_PREVIEW_DIR=/some/dir npx vitest run convex/lib/frame.test.ts` and look at the images.
3. Bump `FRAME_RENDERER_VERSION`.
4. Run `FRAME_GOLDENS=update npx vitest run convex/lib/frame.test.ts` (it refuses to update without the bump) and look at the changed goldens.

To change fonts or the character set, use `scripts/buildFrameFonts.ts`, run from `sunny_backend`. It reads `sunny_app/node_modules/@expo-google-fonts`, so run `npm ci` in `sunny_app` first. Prettier must run on its output. The faces are Literata 0.4.3 and Atkinson Hyperlegible Next 0.4.1, both OFL 1.1 (license texts in `lib/fonts/`). `lib/fonts/frameFontData.ts` is generated: never edit it by hand. Its `FACE_DATA` is an int16 stream that `lib/frameText.ts` reads, so the generator and the reader change together. Only `deviceFrame.ts` may import `lib/frame`, because the font data is about 529 KB.

Packed format (`lib/framePacked.ts`; firmware is written against this):

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 4 | Magic, ASCII `SNYF` (`53 4E 59 46`) |
| 4 | 1 | Format version, 1 |
| 5 | 1 | Bits per pixel: 1, 2, 4 or 8 (the fewest that hold every level; 2 for 4 greys, 1 for 2) |
| 6 | 1 | Encoding: 0 raw, 1 PackBits (the server always sends 1) |
| 7 | 1 | Highest grey level, greys - 1 (3 for 4 greys, 1 for a 1-bit panel) |
| 8 | 2 | Width in pixels, uint16 little-endian |
| 10 | 2 | Height in pixels, uint16 little-endian |
| 12 | 4 | Payload length in bytes, uint32 little-endian (bytes after the header) |

Decoded pixels run in rows from top to bottom, each row `ceil(width * bpp / 8)` bytes. Within a row, pixels run left to right, most significant bits first (at 2 bpp the first pixel is bits 7-6). A pixel's value is its grey level: 0 is black, the highest level is white, and the greys between are evenly spaced (with 4 greys: 0 black, 1 dark grey, 2 light grey, 3 white). Unused bits at the end of a row are 1s.

PackBits runs over the whole pixel stream and may cross rows. Read a control byte `n`:

- `n` from 0 to 127 copies the next `n + 1` bytes.
- `n` from 129 to 255 repeats the next byte `257 - n` times.
- 128 is a no-op (never written).

A decoder must reject:

- a magic other than `SNYF`;
- a version it does not know (a later version may change anything after byte 4);
- an encoding other than 0 or 1;
- more levels than the bits per pixel hold;
- a file whose length is not 16 plus the payload length;
- a payload that does not decode to exactly `height * ceil(width * bpp / 8)` bytes (a run that would write past the end, or a payload that ends early).

The payload is never longer than `raw + ceil(raw / 128)` bytes. For 960 x 680 at 2 bpp, raw is 163,200 bytes and the payload is at most 164,475 (the file at most 164,491). That is the buffer a device must be ready for. A streaming decoder needs only the control byte, a remaining count and the repeat byte, and can hand each finished row (240 bytes at 960 x 2 bpp) to the panel driver. `lib/framePackedDecoder.helpers.ts` is a reference decoder to port.

PNG frames map a level `l` of a grey count that is not a power of two to `round(l * 255 / (greys - 1))`, with halves rounded up. Typical sizes at 960 x 680 x 4 over the golden cases: packed frames are 11 to 28 KB (median about 17 KB), and PNG frames 7 to 15 KB (median about 11 KB). Raw pixels would be 163 KB.

- Chat: the household agent, with Sunny's daily summary posted in the same thread under a "Daily summary" label.

In Chat, Sunny's reply to a request that added or changed tasks is followed by a wording card for each task (`WordingCard.tsx`). - It asks for notification permission once, and only while iOS has not asked yet.
- It registers the APNs token with `households.registerPushToken`, and registers it again when the OS rotates it.
- It unregisters the token on sign-out, before the Clerk session ends. It also unregisters the token whenever the app returns to the foreground with notifications turned off in Settings. APNs keeps accepting pushes that such a phone never shows, so the token must go for the backend to text instead.
- It registers the `caregiver_alert` category with one foreground action, "I'm on it". The action claims the push's task (`instances.claimTaskInstance`) and shows Home. A claim call that fails shows "Could not claim it". When someone else is already on it, the app shows nothing, and Home says who.

A tap made while signed out or during onboarding is discarded (`push.ts` `useDiscardNotificationTaps` in `src/screens/SignedOutFlow.tsx` and `CaregiverOnboardingScreen`), so it never claims a task later.

A phone's token belongs to the caregiver who registered it last. A paired device's token moves only to another paired device, which is the same phone paired again (`households.registerPushToken`, `notes/SCHEMA.md`). If permission is denied, the caregiver stays on SMS. A caregiver with a verified phone is texted whenever their push cannot be delivered: when there is no APNs configuration, when the tokens are dead, or when push retries run out (`notes/SCHEMA.md`). Credentials. Only a session that is `paired` with device kind `senior_phone` gets a token. The app calls `deviceApi.issueToken` when the bridge has no token for the current `CONVEX_SITE_URL`, and stores it with `setCredentials`. It issues again only when no token is stored, which happens after a 401 removed it. The token is a keychain item (service `com.kmsunny.sunny.widget`, account `deviceToken`, accessible after first unlock on this device only) in the access group `$(AppIdentifierPrefix)com.kmsunny.sunny.shared`. The site URL is in the app group defaults (`group.com.kmsunny.sunny`, key `sunny.widget.siteUrl`). Both targets read the group names from their Info.plist keys `SunnyAppGroup` and `SunnyKeychainGroup`. The app lists its own `$(AppIdentifierPrefix)com.kmsunny.sunny` first in `keychain-access-groups`, so Clerk and expo-secure-store items keep their default group. The site URL must be `https`, or `http` for a loopback host only (`SiteURL.parse`). A plain `http` URL to any other host is refused, because it would send the Bearer token unencrypted. Unpair, sign-out and any session other than the senior phone (caregiver, home display, signed out) clear the token, the site URL, the cached timeline and the press queue, and reload the widget. Before the clear, `WidgetSync.clear()` sends what is queued for up to 3 seconds with the old token, and `runUnpair` does the same for the app's own queue, so a press made offline is not lost at unpair. A token that a widget sync's `issueToken` returns after a clear is not stored, and a clear waits for a credentials write already under way. Unpair then revokes the device token on the server with `deviceApi.revokeOwnToken` before it signs out. It is a JavaScript call, because it needs the Clerk session. If storing a token fails, the app stops issuing until the next clear, so a broken keychain cannot burn the limit of 10 tokens an hour.

Files in the app group container, under `SunnyWidget/`:

- `timeline.json`: the last good `GET /device/timeline` body with its ETag. A body is stored only after it decodes and passes the checks (ascending entries, the first at `generatedAt`, every card list ending in exactly one clear card, steps in range, a known time zone).
- `presses/<press id>.json`: one file per Done press. It holds the instance, step, `via` and press time. A press is written to `staging/` and renamed into place, and it is removed by deleting its own file once the server has answered it. No process rewrites a shared list, so the widget extension and the app, where the Live Activity's Done runs, can append at the same time.
- `marks/<press id>.json`: one "pressed" mark per press. A mark is written before its press, so no process can answer a press that has no mark. No process rewrites a mark, so an Undo that removes it while the server's answer is being recorded is never undone.
- `answers/<press id>.json`: the time the server answered the press, written beside its mark and removed with it. An answer whose mark was removed first is dropped 48 hours after the answer. The app writes marks for its own presses here too (see "Presses shared with the app" below). The widget hides a card whose instance and step have a mark.
- `credentials.lock`: a `flock` lock held only while the token is written or removed, so a 401 removes a token only if it is still the one that got the 401.
- `widgetPush.json`: the WidgetKit push token on iOS 26 and later. Clearing the credentials keeps it, because it belongs to the phone and not to the pairing.

Presses. `WidgetSync.pressDone(instanceId:step:via:)` is the one entry point for a Done press. When the keychain says the phone has no device token, it stores nothing and returns `noCredentials`, so no press is kept that a later pairing would send with another household's token. A keychain it cannot read, before the first unlock after a restart, does not count as no token. Otherwise it appends the press, then replays the queue for at most 4 seconds, and returns. `WidgetSync.replayPresses(timeout:)` sends queued presses oldest first as `POST /device/confirm` with `pressedAgoMs` computed at send time. The timeout is one budget for the whole replay. Any 200 answer (`confirmed`, `advanced`, `rejected`) and a 400 delete the press and record the answer's time beside its mark. A 401 keeps the queue, deletes the token and stops. A 429 or no network keep the press and stop, since every later press would get the same answer. A 5xx keeps the press and holds back only the later presses of the same task instance, so the steps of one task never go out of order and other tasks still go out. The queue is replayed by every timeline request, every Done press and by the app when it comes to the foreground. The client sends every press and leaves the judgment to the server. A press the server refused is deleted after the answer, and a later fresh timeline shows the task again: on a fresh timeline (200 or 304), a mark is dropped only when the server answered its press before that fetch started. A press answered while the fetch was in flight keeps its mark, because the server may have built the timeline before it applied the press. A mark that no answer can reach any more (a crash between the two writes) is dropped 48 hours after the press.

Presses shared with the app. The Today screen, the widget and the Live Activity each hide a task that one of the others pressed, by one rule per side. The app reads the native queue's unsent presses (`unsentPresses`) when it comes to the foreground, after each widget sync and after each `syncSurfaces`, which runs whenever the day view changes, so a press that was sent while the app was open leaves the overlay once the server's answer reaches the day view. It merges them with its own queue by press time (`overlayEntries`), and replays the merged list over the day view with `applyPending`. In the other direction, `confirmQueue.watchPresses` reports each app press when it is stored, when the server answers it and when an Undo or expiry withdraws it. On the paired senior phone `useWidgetSync` attaches `widgetPressMirror`, which calls `markPressed`, `answerPress` and `withdrawPress`. `markPressed` writes a mark (no press file, since the app sends its own press), applies `PressEffect` to the task's Live Activity and reloads the widget. A press in the app on the last step ends the activity at once with no receipt, because the app shows its own "Noted" and the server keeps the receipt only for a press made on the activity, so its end push would dismiss a receipt at once anyway. A press on an earlier step shows the next step, as on the activity. `answerPress` records the answer time beside the mark, and `withdrawPress` removes the mark and its answer and reloads the widget.

Timeline and reload policy. Each timeline request replays the queue, then fetches the timeline. It sends `If-None-Match` only while the cached timeline's `until` is more than 2 hours away, so the cache is renewed before it runs out. Entries become one WidgetKit entry per slice, leaving out a slice that would show the same as the entry before it, plus a "Not connected. Open Sunny to update." entry at `until`. The widget asks again in 15 minutes while a task card shows or will show within an hour, in 60 minutes otherwise, never later than 2 hours before `until`, and no earlier than a 429's `Retry-After`. With no network or a malformed body it uses the cache. Without credentials, or after a 401, it shows "Open Sunny to see your day." The gallery snapshot and placeholder show a sample task; a real timeline never does.

Layout rules. Measurements are in `WidgetStyle.swift`. Text follows Dynamic Type with one factor taken from the body style's sizes. Each system widget uses the largest factor at which its content fits the widget's height and the when-line fits its width; below the design size, insets, gaps, tag padding and the Done key shrink with it, the Done key never below 44 points and no text below 13 points. The medium widget shows the sentence (or a step's text) when it fits on one line, else the label. Long lines wrap at word breaks measured with Core Text and keep the design's line heights. Clear and Tinted styles and the lock screen use a translucent tag, an outlined Done key and no glow.

Who runs where:

- The app process runs the reporter, the Done intent and the background refresh. The system runs a `LiveActivityIntent` in the app's process and launches the app in the background for it.
- The extension draws the activity and owns the WidgetKit push token. When the token changes it stores it in `widgetPush.json` and sends a report with only the `widgetPush` section. The app's later reports include the stored token, so a send that failed in the extension is repeated by the app.
- React Native handles no token. It calls `syncSurfaces` when the app comes to the foreground and whenever the day view changes, which covers an in-app Done or Undo once the server has answered it.

Reports. The phone sends one at every process launch while it has a device token (or cannot read its keychain yet), when `setCredentials` stores a token, on every token, enablement, new-activity or activity-state change, after a Done press on the activity, when a background refresh push arrives, and when React Native calls `syncSurfaces`. Each report is read from ActivityKit when it is built. Nothing is queued. A failed send is repeated by the next trigger. A report run also reloads the widget timelines when one of the requests folded into it can change what the widget shows: a background refresh push, `syncSurfaces`, or a press marked in the app or on the activity (`SyncTrigger` in `core/SyncLane.swift`). Token, enablement, new-activity and activity-state changes and the launch report do not reload, since each reload spends the widget's daily reload budget when the app is in the background. Withdrawing a press and clearing the credentials reload the widget themselves. Before each report the phone ends any second activity with the same `activityKey`. It keeps the first one that ActivityKit lists. The report lists each key once, activities on screen first, and at most 8 activities.

Applying the reply. An `update` directive changes an activity on screen only when its content or stale date differs, and an `end` directive ends it at once, with its current content when the directive's content is null. A directive for a key that is not on screen does nothing, so applying the same reply twice changes nothing the second time. A 401 to the report, or to a press replayed by the intent or the refresh push, ends every activity on the phone. The 401 also removes the token by the widget's rule.

Done on the activity. The intent calls `WidgetSync.pressDoneOnActivity`, which goes through `pressDone`. When the keychain says the phone has no device token, for example an activity push-started after an offline unpair, `pressDone` stores nothing and the activity call ends every activity, so it shows no receipt. Otherwise it stores the press with `via: "live_activity"`, applies `PressEffect` to the activity as soon as the press is stored (on the last step it ends the activity with the receipt and dismisses it `receiptMs` later), and then replays the queue for at most 4 seconds. When the press could not be stored, it is sent directly and the activity waits for the server's answer. It shows the receipt, or the next step, only when the server answered `confirmed` or `advanced`. A refusal, a 400 and no answer show nothing. Then the intent sends a report.

Unpair and sign-out. `clearCredentials` ends every activity, sends a report that clears all three sections, then clears the credentials, in the same queue as the reports, so no report with the old tokens can follow it.

Layout. The banner follows the Figma measurements (386 x 112, inset 14). The banner shows the label, then the step's text for a task with steps or the detail otherwise. The expanded island shows the sentence or step text when it fits on one line, else the label. The compact view shows the task's symbol and a "Now" tag that becomes a yellow dot when only a 28-point circle is available. Each `icon` maps to an SF Symbol in `TaskIcon.symbolName` (`pills` is `pill`; a card without a known icon gets `clock`), and the accessory widgets use the same mapping. Text in the activity does not follow Dynamic Type, because the system caps the banner's height. The views were checked by rendering them on macOS for each face, with the Dynamic Island regions placed by hand, since ActivityKit and the Dynamic Island do not exist on macOS.

Not verified, since nothing was run on a simulator or device:

- that a push-started activity appears, and that ActivityKit matches `"attributes-type": "SunnyTaskAttributes"` to the type, which is declared in the `SunnyWidgetCore` module;
- that the app is launched for the Done intent, including after a force-quit, and that a locked phone asks the senior to unlock before the press counts;
- that `didFinishLaunching` runs before the token sequences deliver their first values on a background launch, and how soon the first report reaches the server;
- that `Activity.activities` lists activities in the order they started, which decides which duplicate is kept;
- the WidgetKit push token on iOS 26, and that the extension's send finishes before the system suspends it;
- the fonts and the glow as WidgetKit draws them on the Lock Screen and in the Dynamic Island;
- VoiceOver on the activity.

The widget extension cannot end activities on a 401 it gets itself (from a timeline request). The token is removed then, and the app's next report ends every activity when the keychain says the token item does not exist (`errSecItemNotFound`). A keychain it cannot read, for example before the first unlock after a restart, is not treated as missing credentials, and that report sends nothing and ends nothing.

Times on the Live Activity, the "Noted at" receipt included, are in the household's zone that the start push carries in its attributes, as on the widget. A zone that iOS does not know falls back to the phone's zone. A Done in the app that is undone after the app marked it natively cannot bring back an activity that the press already ended; the server starts one again only when the Undo reaches it and reopens a task it had confirmed. When the press and the Undo are both made offline, the task shows as due again in the app and on the widget, but has no Live Activity while the phone stays offline. Once it is online, the app sends the press and then the Undo, the server confirms the task and reopens it, and the reopen queues a reshow (`senior_reshow`) that starts the activity again.

## sunny_agent

A LiveKit Python worker. Its modules:

- `src/agent.py`: the `Assistant` and `entrypoint`.
- `src/prompts.py`: the system prompt, which follows the spec's voice guardrails, and the formatting of household context.
- `src/tools.py`: helpers behind the household tools, and the formatting of spoken times. Web search is `Assistant.web_search` in `agent.py`.
- `src/speech_guard.py`: checks on each model reply before it is spoken. A reply may have no words before a tool call, may not say "family was told" without a tool result behind it, and may make no promises about what family will do. The guard also handles the same-or-another dose question.
- `src/weather.py`: Open-Meteo geocoding and forecast for `households.weatherLocation`, with no key.
- `src/memory.py`: resolving the household from participant metadata, logging the conversation, and the post-call summary and question extraction.
- `src/convex_client.py`: the HTTP client for the `agent:*` Convex functions. `query_as` and `mutation_as` validate each return value against its type in `src/convex_types.py`.
- `src/config.py`: endpointing constants tuned for seniors, and the emergency numbers.

United States only for now: Sunny assumes the household is in the US. The numbers the agent gives (911, 988 for the crisis line, Poison Control 1-800-222-1222) are `EMERGENCY_NUMBER`, `CRISIS_LINE` and `POISON_CONTROL` in `src/config.py`, the one place they are kept. A household elsewhere needs those numbers to come from the household first.

Tools: web_search, get_weather, list_today, confirm_task, snooze_task, medication_status, log_dose, undo_last_dose, create_reminder, cancel_reminder, remember_fact, flag_caregiver, send_family_message, read_latest_message, add_to_list, read_list, take_off_list (`src/list_tools.py`). No tool depends on the phone, because the senior talks through the home display.

A Talk session opens silently and listens. Only a session started by a task that is due or escalated speaks first, with the task's fixed prompt. A bare greeting gets "I'm listening."; "ok" alone never confirms, "no" alone never snoozes, and "yes" confirms only as the answer to the agent's own question about that task. A one- or two-word transcript that repeats the end of the agent's last line is treated as echo.

Self-reported doses: when a report may repeat a dose already written down, the agent asks about it ("the same one or another?"), and `log_dose(another=true)` logs it. A dose can be taken back only in the conversation that logged it, and only within 30 minutes. A distress flag always gives the emergency numbers, and a fall counts as distress.

Multi-step tasks: the session remembers which step it read out (`StepsRead` in `src/tools.py`). That is the opening prompt's step at first, then the step in each `confirm_task` result. `confirm_task` sends that step when the spoken name matches exactly one remembered task; the model never passes a step. A confirm on a step the task has left answers `other_step` and changes nothing. A confirm on a step that is not the last returns the next step to read out.

The worker ends a session after 60 seconds with no speech (`INACTIVITY_TIMEOUT_S`). Speech is slowed by using Cartesia `sonic-3` at speed 0.85 (`TTS_MODEL`, `TTS_SPEED` in `src/config.py`).

Weather: the agent looks up `households.weatherLocation`. After deploy, the product owner sets it to "Brooklyn, NY" with one command from `sunny_backend/`: `npx tsx scripts/caregiver.ts weather-location "Brooklyn, NY"` (or `households.update` from the caregiver app). With no location set, the agent falls back to web search.

Run (from `sunny_agent/`): `uv sync`, then `uv run python src/agent.py download-files` once, then `uv run python src/agent.py dev` (or `console` to talk in the terminal). Tests: `uv run pytest -q`. Some tests call the model and need `ANTHROPIC_API_KEY`. Type and lint checks: `uv run mypy src/ tests/` (strict settings in `pyproject.toml`; no `type: ignore`), and ruff via pre-commit. Modules import each other at the top level (`from tools import ...`). `src/` is not a package, and mypy resolves it through `mypy_path`.

Environment (`sunny_agent/.env`, git-ignored; copy it from `.env.example`): `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, `ANTHROPIC_API_KEY`, `DEEPGRAM_API_KEY`, `CARTESIA_API_KEY`, `TAVILY_API_KEY`, `CONVEX_URL`, `SUNNY_AGENT_KEY` (must equal the value on the Convex deployment), and optional `DEV_HOUSEHOLD_ID` (used when the session has no household in its metadata).

## Contracts the code relies on

The code has no comments, so these rules are not visible in it. They must hold.

Backend (Convex):
- Files named `*.helpers.ts` (two dots) are not function modules. `_creationTime` is the implicit last field of every index. `undefined` sorts first. Patching a field with `undefined` clears it. There are no unique constraints, so every writer checks first. Per-mutation limits force batching.
- Times: epoch ms on the wire; local dates are `YYYY-MM-DD`, local times `HH:MM`, and weekdays ISO (1 = Monday). Events are stored in local terms. `DAY_MS` is not a local day. In a spring-forward gap, a time uses the offset from before the change; a repeated time takes the later instant (as Postgres does). Queries that read `Date.now()` do not re-run as time passes, so clock-dependent queries take a `minute` argument that the client bumps.
- Order: `scheduler` runs `fireSteps` before `closeWindows`. `closeWindows` sends the caregiver alert that a short window skipped. The household check stays first in `instances` mutations. `resyncHouseholdTimezone` writes the new zone before it recomputes instances. The tick calls `sweepLiveActivities` after its last state change, because `instanceChanged` leaves the scheduler's own changes to that sweep. `changeInstance` and `deleteInstances` call the Live Activity hooks after their write. `delivery.begin` checks that the instance is still due before it opens an activity row, and every way an outbox row leaves `pending` goes through `settle` in `delivery.ts`, which marks the row's activity started or closes it. The one exception is the phone's report of a `starting` activity, which settles the cue and sets the activity's phase in the same mutation (`lib/liveActivity.ts`).
- Undo: the server allows 60 s, and the app offers 30 s. The HTTP device API must keep refusing `pressId`.
- Device state (firmware JSON): an absent value is `null`, never a missing key. `version` is FNV-1a 64 over canonical JSON without `generatedAt`. `displayVersion` covers only drawn fields. `utcOffsetMinutes` is minutes east of UTC.
- Secrets: device tokens, OAuth refresh tokens and phone codes are generated or encrypted only in actions. The plaintext is never stored, logged or put in scheduler args. A wrong phone code returns a status instead of throwing, because a throw would roll back the attempt count.
- Agent runtime: a workflow body must stay stable while runs are in flight. The Managed Agents event list lags, so the baseline is written before posting. A tool's effect and its `agentToolCalls` row share one transaction. There is one in-progress request per session, and a continuation keeps its session's fingerprint and config. The poll loop stays under the 10-minute action limit. Untrusted text that reaches a prompt goes through `lib/text.ts` and `agentHistory.ts`.
- LiveKit room metadata keys are exactly `household_id`, `device_id`, `trigger`, `task_instance_id`. The server picks the room and the identity.
- Twilio: `TWILIO_WEBHOOK_URL` must match the console URL exactly, because the signature covers it. The signature is checked before the body is read. Sunny never replies to opt-out keywords. Only the newest alert of the last 24 hours can be claimed by text. XML 1.0 control characters are stripped from TwiML. SMS bodies are capped at 1500 characters (Twilio's limit is 1600).
- APNs needs HTTP/2, so `apns.ts` is a `"use node"` file and cannot hold mutations. Time-sensitive pushes need the iOS entitlement. Custom keys sit beside `aps`. The provider token is reused for 20 to 60 minutes. Only a 410 deletes an alert token, the Live Activity start token or the widget token. An activity's update token is also dropped on any other answer that is final (not a 429 and not a 5xx), because the tick would otherwise send the same refused push every minute for up to 12 hours. `apns.send` knows nothing about payloads: every body and header comes from a builder in `lib/apnsPayload.ts`, and the topic suffix follows the push type (`TOPIC_SUFFIX`). Widget refresh pushes carry expiration 0 so that a stored one never replaces a stored prompt.
- Clerk: the JWT template is named `convex` and maps `sunny_kind`. Device users need usernames (optional usernames enabled on the instance). A 422 `form_identifier_exists` is retried once.
- Google Calendar: event ids are base32hex, so Convex ids are hex-encoded into them. A deleted id stays reserved, and an upsert restores that event. A 403 can be a rate limit, a 409 can be a concurrent create, and a 404 may mean the event rather than the calendar. End times are wall-clock arithmetic. `UNTIL` is the end of the last local day, in UTC.
- Limits: "up to N a day" on a dose applies to both the trailing 24 hours and the local day. Digest lines fit in 600 characters (`LINE_MAX` x `MAX_LINES`).
- Tests run in vitest's edge-runtime, to match Convex. The phone tests mock `./apns` with an async factory. When two scheduled functions import that module for the first time at the same moment, one of them gets the real module and answers "APNs is not configured". `phoneHousehold` in `phoneHarness.helpers.ts` therefore imports `./apns` before anything is scheduled. `settle(t, ms)` moves the fake clock forward by exactly `ms`, one timer at a time, and waits after each timer until every scheduled function that started has finished. It throws if that wait takes more than 4 seconds of real time, which is below vitest's 5-second test timeout.

App (sunny_app):
- `registerGlobals` runs before any LiveKit use. Provider order: SafeArea, Theme, Tuning, Clerk, ConvexProviderWithClerk, Voice.
- `households.mine` is skipped until Convex confirms auth, because an empty answer would read as the device being removed.
- Done queue (`pendingConfirms.ts`): nothing is sent while the socket is down, because Convex would hold the call and resend it later with a stale age. An unanswered send is awaited again, not sent again. An entry is removed only when the server answers. A 401, a 429 or a network error blocks the entries behind it. Time offline does not count toward the stuck threshold. `clear` runs on the write chain with a generation counter. An entry is visible only after its write finishes. While entries wait, each task's queued presses and undos are replayed in order over the server's state (`pendingEntries.ts`).
- iPad display: iPadOS 26 does not reliably honor an orientation lock. The panel scale is clamped at 0, because a negative scale mirrors the panel. Fonts load before any text is laid out; otherwise the fallback font sticks.
- Audio: the chime keeps the audio session active, so speech right after it is not cut off. LiveKit takes the session for a call and releases it afterwards (`autoConfigureAudioSession`). Metro bundles an asset only through `require`.
- Voice: phone RPCs are registered only on the phone, and a contacts dialog or SMS composer must never cover the display. The display's agent connect timeout is the longest tunable, so the display's own start timeout fires first. The SMS composer is opened without awaiting it, because the agent's RPC times out after 10 s. RPC responses are capped at 15 KiB, and RPC logs carry only lengths and counts. Muting does not release the microphone. The pre-connect track handle is read from livekit-client's private `pendingPublishPromises`, since there is no public API for it.
- Push: "I'm on it" opens the app to the foreground, so the claim runs with the Clerk session.
- Caregiver fields report their own focus, because a hardware keyboard fires no keyboard events. The `inactive` app state does not flush unsaved edits.
- The developer pill opens only on a long press on the display. Saved tunables apply only in `__DEV__` builds.

Voice agent (sunny_agent):
- `ctx.connect()` runs before `resolve_session`, because participant metadata exists only after connecting. The shutdown callback is registered right after the Convex client is created, so the client closes even when setup fails. Shutdown order: finalize the conversation, drain turn writes, close the client. Finalize writes the end time before the model call, so a slow or failing model never loses it.
- Convex errors are redacted before logging, because a validation error can echo the args, and the args hold the agent key. Queries are retried once on a connect failure, since they are idempotent; mutations never are.
- `src/convex_types.py` copies the return types of the `agent:*` functions in `sunny_backend/convex` (`lib/today.ts`, `lib/agentContext.ts`, `lib/voiceTasks.ts`, `lib/voiceDoses.ts`, `lib/voiceRouting.ts`, `lib/householdList.ts`, `instances.ts`). A call whose value does not match its type fails with `ConvexError("bad_response")`, so a field renamed or made optional on the backend must be changed there too. Convex leaves a field out when its value is `undefined`; a field the backend can leave out is `NotRequired`. The `TypedDict`s come from `typing_extensions`, because pydantic cannot validate `typing.TypedDict` on Python 3.11, which the Dockerfile uses.
- Cartesia applies `TTS_SPEED` only on `sonic-3` (0.6 to 2.0), so changing `TTS_MODEL` silently drops the slow-speech guardrail. `ECHO_DETECTION_WINDOW_S` must exceed the longest spoken line (about 10 to 15 s). Endpointing waits long because seniors pause mid-thought. Interruption needs two words, so coughs and the TV never barge in.
- A Talk press opens silently, because a spoken cue echoed through the mic would pass the echo filter and be answered as if the senior had said it. The reply to a bare greeting is exactly "I'm listening." so that its echo can never confirm a task.
- The speech guard exists because Claude Haiku said "I've let Anna know" without calling the tool, in repeated runs. Its cost is that speech starts only once a reply is complete. The guard looks for the `SAME_OR_ANOTHER` prefix to speak the exact dose question.
- Tool descriptions the model sees come from `@function_tool(description=...)` and `Annotated[..., Field(description=...)]`, not from docstrings. Tavily is created on the first search, so a missing key disables only web search. It runs in `to_thread` because it is synchronous.
- `voice_llm()` turns on prompt caching with the LiveKit plugin's `caching="ephemeral"`. Anthropic caches a request as a prefix in the order tools, system prompt, messages. The plugin marks the last tool, the system prompt, the newest assistant message and the user message before it, with the 5-minute TTL. Claude Haiku 4.5 caches a prefix only when it is at least 4096 tokens and skips a shorter one without an error. The smallest prompt, a session with no household, comes to about 5,250 tokens with the tools, so trimming about 1,150 tokens from the prompt or the tool descriptions turns caching off. `tests/test_prompt_caching.py` catches that, but it needs `ANTHROPIC_API_KEY` and CI does not run it, so run it after changing the prompt, the tools or `LLM_MODEL`. Keep the system prompt and the tool list the same for the whole session, because a change to either writes the prefix to the cache again at 1.25 times the input price.

## Checks

Style is enforced by pre-commit: run `uv tool run pre-commit run --all-files` from the repo root. It runs ruff, ruff-format and mypy for `sunny_agent`; prettier and tsc for `sunny_backend/convex` and `sunny_backend/scripts`; and prettier, eslint and tsc for `sunny_app`. Two more hooks reject comments in code anywhere in the repo. `sunny_agent/scripts/no_comments.py` flags Python comments (`# type: ignore` and `# noqa` included), docstrings and other bare string statements, and a mypy `ignore_errors` setting in a `pyproject.toml`. `sunny_backend/scripts/checkNoComments.ts` flags every comment in .ts, .tsx and .js files, which covers `eslint-disable`, `@ts-ignore`, `@ts-expect-error` and JSX `{/* */}`; `convex/_generated` and `node_modules` are skipped. Both use the language's own parser, so a `#` or `//` inside a string, template, regex or JSX text is not flagged. They cannot catch a workaround written without a comment, or a check loosened in configuration (ruff `per-file-ignores`, a rule turned off in an ESLint config, a tsconfig setting); those are left to review. A shebang or a `# -*- coding` line counts as a comment too. Run `npm install` in `sunny_app` and `sunny_backend` first. Before committing, run `/simplify` and the TLM code reviewer (see `CLAUDE.md`).

# Shared State Schema (Convex)

How Sunny's Convex tables implement `notes/SPEC.md`. The source of truth is `sunny_backend/convex/schema.ts` (every field is commented there); this file explains what each table is for, who writes it, and the rules the code keeps because the database does not. Enums live in `convex/lib/validators.ts`. History of the move from Supabase: `notes/CONVEX_MIGRATION.md`. Background work: `notes/AGENT_RUNTIME.md`.

## Conventions

- **Instants** are epoch milliseconds (`number`), for example `windowStart`, `expiresAt`, `settledAt`. Convex's own `_creationTime` is also epoch ms, but the scheduler uses explicit `createdAt` where tests must drive the clock.
- **Household-local dates and times** are strings: `"YYYY-MM-DD"` and `"HH:MM"`. Schedules are stored in local terms so 8:00 stays 8:00 across DST; the instant is computed from the household's IANA region timezone (`lib/time.ts`, no dependency). Weekdays are ISO numbers, 1 = Monday.
- **User ids** are Clerk user ids (the identity's `subject`). A senior device is also a Clerk user, created at pairing with `public_metadata.sunny_kind = "device"`.
- **View shapes use `null`.** Results built for the apps (`calendar.dayView`, `listEvents`, `instances.today`, `confirmDueTask`) return `null` for an absent optional value, never a missing key. Raw document returns keep Convex's omitted-field shape.
- **Uniqueness is kept by code.** Convex has no unique constraints. The writing mutation looks the key up through an index first (serializable transactions make check-then-insert safe). Keys: one instance per task, local date and time; one join code per value; one connection per caregiver per household; one verification per member; one digest per household and local date; one sync per event and connection; one `agentToolCalls` row per request and tool use id; one `eventNotices` row per event and date.
- **Actor model.** `actorKind` is `caregiver`, `senior_device`, `agent` or `system`. Every write path records who acted (`createdVia`, `confirmedVia`, audit rows). The household agent's actor also carries the caregiver it acts for (`onBehalfOf`) and its request (`requestId`): `actorUserId` returns that caregiver, so what the agent creates has `createdBy` = the requester and its audit rows have `actorUserId` = the requester and `detail.requestId`. The voice agent carries neither. Public functions resolve the caller through `lib/access.ts` (`requireReader`, `requireEditor`, `requirePrimary`, `requireSenior`) and reject device identities from every caregiver check. Backend-only work is an `internal*` function. The Python voice agent calls `agent:*` functions with `SUNNY_AGENT_KEY` as the first argument; it may pass `now`. Public functions never accept `now` from clients.
- **Deletes.** Events are soft deleted (`deletedAt`) so cancellations sync to Google. Tasks are hard deleted through `tasks.remove` / `purgeTaskData`, which also remove their instances and notifications. There is no household delete yet.
- **Audit.** `lib/audit.ts` writes `auditLog` rows from the mutations that change audited tables. It is called explicitly; nothing is automatic.

| `devices` | A paired senior device: `userId` (its Clerk user), `kind` (`senior_phone`, `home_display`), `name`, `lastSeenAt`, `pairedAt`, `pairingNonce` | `by_user`, `by_household` | `households.pairDevice` (internal, called by `pairing.ts` `/pair`), `removeDevice` |
| `pushTokens` | Raw APNs tokens per user | `by_user`, `by_token` | `households.registerPushToken` / `unregisterPushToken` |

Rules:
- A caregiver belongs to at most one household: `households.create` and `redeemJoinCode` reject a caller who already has a `householdMembers` row ("invalid"), and the check runs before anything is inserted (a rejected redeem leaves the code unused). A caregiver removed by `removeMember` can then create or join another. The rule is enforced in code, not by an index, and older rows may still hold two memberships.
- A household always keeps at least one primary: the last primary cannot be demoted or removed.
- A device's `userId` is a Clerk user made at pairing. Re-pairing creates a new user, so a push token held by an orphaned user (no device row, no membership) may be taken over; a token held by a live account is refused.
- `pairingNonce` and `pairedAt` support retrying a lost `/pair` response for 10 minutes. `listDevices` strips the nonce.
- Removing a member drops their Google connections, links and pending syncs and revokes the grants.
- `backgroundPaused` is read by every workflow step, workpool job, the scheduler and the digest. Resuming re-pushes calendars (`households.update`).

State machine (`instanceState`):

```
upcoming --(window_start)--> due --(caregiver alert step fires)--> escalated
   |                          |                                      |
   +--(confirm, <=60 min early)+--(confirm)--> confirmed <--(confirm)-+
                              |                                      |
                              +--(window_end, unconfirmed)--> missed <+
due / escalated / missed --(caregiver marks done)--> resolved
missed --(senior confirms late)--> confirmed (late = confirmedAt > windowEnd)
confirmed --(the same senior device undoes, <=60 s after the server recorded it)--> the state before the confirm
confirmed / resolved --(editor caregiver reopens, confirmed today)--> upcoming | due | escalated | missed, by the clock
```

Rules:
- `instances.ts` is the single write path for every surface. A senior device or the agent produces `confirmed`; a caregiver produces `resolved` with `confirmedVia = caregiver`. Confirming an already confirmed or resolved instance returns the original result. `confirmDueTask(household, via, label?)` is what the Done button, widget and voice call; it returns a status (`confirmed`, `already_done`, `nothing_due`, `not_found`, `ambiguous`, `not_due_yet`), so the double-dose guard lives in one place.
- Every confirm records the state and snooze it replaced in `resolvedFromState` and `resolvedFromSnoozedUntil` (device, agent and caregiver alike; the names date from the caregiver resolve). **Senior undo** (`instances.undoPressedTask`, senior devices only): the phone shows Undo for 30 seconds; the server allows `SENIOR_UNDO_MS` (60 s) so a slow network never refuses a press the senior was offered. It needs state `confirmed`, `confirmedBy` equal to this device's user id (not another device's, the voice agent's or a caregiver's confirm) and `now - (confirmReceivedAt ?? confirmedAt) <= SENIOR_UNDO_MS` (measured from when the server recorded the confirm, because an offline press carries an earlier `confirmedAt`). It also needs the task to still run (same test as reopen; else `too_late`). Measured from `confirmedAt` for a press that took 1 to 5 minutes to arrive (no `confirmReceivedAt`), such a press lands already past 60 s; accepted, the phone's Undo has expired by then. It restores the prior state (by the clock, as a reopen does, when none was recorded), the snooze, and clears the confirmation fields; audited as a `state_change` with `undo: true`. Any failed condition returns `{ status: "too_late" }` and changes nothing; it never throws for a late tap (only `forbidden`: not a senior device, or another household's instance). The caregiver's own 30 s `undoResolve` only applies to `resolved`, so it cannot touch a device's confirm. **Caregiver reopen** (`instances.reopenTaskInstance`, editors only; the home display has no undo): allowed when state is `confirmed` or `resolved` (whoever confirmed it) and either the household-local date of `confirmedAt` or the instance's own `localDate` is today's (the second covers a 00:30 task confirmed at 23:45 the evening before; `invalid` otherwise; the task must still run, i.e. exist, be active and still be timed at that time or anytime to match, else `invalid` "This task is no longer on the schedule." because deactivating or editing a task deletes only its open instances;  viewers, devices and other households are `forbidden`). The new state is by the clock (`lib/confirmRule.reopenedState`): before `windowStart` `upcoming`; inside the window the recorded prior state if it was `due` or `escalated`, else `due`; at or after `windowEnd` `missed`. Anytime instances never escalate, so inside their window they reopen as `due`, and after it as `missed`. The confirmation fields and `resolvedFrom*` are cleared; the note and any claim are kept; no snooze is restored. Undo and a reopen of a device confirm set `confirmTakenBackAt` (to `now`, or to the offline tap time): `confirmInstance` refuses (`invalid`) a press carrying an age whose press time (`now` minus the age) is at or before it, so a press the device's durable queue still holds after its acknowledgement was lost cannot confirm the task again; through `confirmPressedTask` this is `{ status: "rejected" }` with the usual `press_not_applied` audit row. A press without an age (the home display's live confirm, voice, a caregiver's Mark done) is not checked against the stamp, since it is by definition made now; a press made after the take-back confirms as usual. A reopen stamps only a device or voice confirm (`confirmed`), not a caregiver's `resolved`, because nothing was taken back from the senior. An Undo tapped offline carries `undoneAgoMs`: the 60 s rule is judged at the tap time and the stamp is the tap time clamped to between `confirmedAt` and now, so a Done pressed after the Undo tap still applies when delivered later. A caregiver alert skipped as `instance_closed` while the instance was done is not re-sent after an undo or reopen. The ladder just continues: steps in `firedSteps` are not repeated and unfired steps fire when due (a reopen late in the window can fire an overdue step on the next tick; only the latest of each kind notifies). Audited as a `state_change` with `reopen: true` and the previous `confirmedAt`, `confirmedBy`, `confirmedVia` (the previous state is `from`). The day view's `reopenable` flag (`TodayEntry`) is the same time, state and task-still-runs rule (`caregiverCanReopen` and `taskStillRuns`), so the app never offers a Reopen that will fail; the role is the mutation's check.
- The scheduler tick (`scheduler.ts`, every minute) fans out one `tickHousehold` per household: expand today and tomorrow (idempotent through the `by_task_date_time` lookup; a window that already closed is skipped unless the task existed when it opened), open windows, fire each due escalation step once (recorded in `firedSteps`; when several steps of one kind come due together only the latest is sent and the rest record `notified: false`), mark instances with a fired caregiver alert `escalated`, and close windows to `missed`. Offsets count from the later of `windowStart` and `createdAt`. Snoozes defer senior prompts only; `skipIfClaimed` steps stop once claimed.
- Editing a task's schedule or the household timezone deletes future `upcoming` instances and re-expands; deactivating a task removes its open instances.
- Seeded policies: **Medication** (0 min prompt, 15 min reprompt, 30 min on-call alert, 45 min all caregivers unless claimed) and **Prompt only** (0 min prompt). Seeded policies cannot be deleted or re-keyed. A task with no policy shows on the surfaces and in the digest but never notifies, so `createTaskCore` (used by `tasks.create` and the agent's `add_task`) assigns a default when no `escalationPolicyId` is given: the household's `medication` policy for `medication` tasks, `prompt_only` for every other type (looked up by `systemKey`; an explicit policy wins; a household missing the seeded policy still creates the task with none). Changing a task's type across the medication boundary (to or from `medication`), in `tasks.update` or the agent's `update_task`, switches the policy to the new type's default when the current policy is one of those two seeded policies; a custom policy is left alone, and a policy given in the same update wins. To fix older tasks with no policy run once: `npx convex run tasks:backfillDefaultPolicies` (no arguments; it also re-assigns tasks whose policy a caregiver deliberately cleared). Senior reminders use the prompt-only policy, found by `systemKey`, so renaming is safe.
- Policy `steps` are embedded. Instances record fired steps by step id, so editing the ladder never makes a step look fired or unfired.

Rules:
- Occurrences are computed (`lib/occurrences.ts`), not stored. Repeats are weekly only.

- Refresh and access tokens are AES-GCM boxes (`lib/secretBox.ts`) keyed by `CALENDAR_TOKEN_KEY`; they are never returned to clients. Rotating the key means caregivers reconnect.
- One connection per caregiver per household is kept by `saveConnection`, which reactivates the existing row.

## Notifications and delivery

| Table | Purpose and key fields | Indexes | Written by |
| --- | --- | --- | --- |
| `notificationOutbox` | The only place notifications are queued. One recipient per row: `recipientDeviceId` (APNs) or `recipientUserId` (SMS). `kind` (`senior_prompt`, `caregiver_alert`, `event_notice`, `digest`, `agent_flag` (the voice agent asking a caregiver to look in; `payload.reason`, `payload.flaggedAt`), `family_message` (a message the senior dictated to family)), `title`, `body`, `payload`, `state` (`pending`, `sent`, `skipped`, `failed`), `channel` (set only when sent), `settledAt`, `attempts`, `attemptStartedAt` (lease), `detail` (skip reason or internal error, never returned to clients) | `by_recipient_kind` (reply-to-claim), `by_recipient_device`, `by_task_instance` (cascade on instance delete), `by_household`, `by_state` | Inserted only through `insertNotification` in `lib/delivery.ts` (scheduler, event notices, digest, `lib/voiceRouting.ts` for agent flags and family messages); settled by `delivery.ts` |

Rules:
- A row leaves `pending` once. Recipient, membership and content are re-checked at send time, so a stale or unreachable row is `skipped` with the reason in `detail`.
- `attempts` is capped (`MAX_ATTEMPTS`) so the sweeper never loops on one row; `attemptStartedAt` is a 5-minute lease the sweeper respects.
- `agent_flag` and `family_message` rows go to caregivers by SMS and never carry the "Reply 1" claim hint (they are not tied to a task); a "1" texted back after one of them claims nothing. Rows are queued only for caregivers with a verified phone: an `agent_flag` goes to the on-call caregiver when reachable, else to every reachable caregiver (distress: always every reachable caregiver); with nobody reachable nothing is queued, the decision is audited and the voice agent says family could not be reached. Only an identical event repeats: a flag whose key (the model's reason plus its detail text; for a medication limit or repeated use, the reason and the task) went out within 10 minutes is not sent again (repeated as-needed use: once a week), and that decision is audited too. At most 12 symptom, money and scam flags per household per hour (distress, help_requested, medication limits, repeated use and dose corrections are never capped); at most 10 senior messages per hour; an identical senior message within 2 minutes is not sent again, and the agent says how the first one went. A "1" texted back after a flag or family message gets "Thanks. Nothing needs claiming for that message." Flag text is at most two sentences and 240 characters, with runs of 6 or more digits removed. A timed-out text is retried only for `caregiver_alert` and `agent_flag`.
- Only tokens APNs reports unregistered are deleted from `pushTokens`.

Rules for the caregiver write path (`profile.ts`):
- Editors (primary, member) write. All four lists are caregiver only (`requireCaregiverReader` in `lib/access.ts`: any role, never a paired device), since what they hold is written about the senior and nothing on the senior's screens uses them. `listMessages` returns `mine` for the caller's own messages and no member ids. Every change writes an `auditLog` row (`lifeProfileEntry`, `sensitiveTopic`, `agentMemory`, `familyMessage`); an update's or correction's row also holds the previous text (`detail.previous`), so a replaced value can be recovered. `requireCaregiverReader` (like every caregiver check) refuses a device by its token claim or by a `devices` row.
- Text is trimmed and capped: name 120, details 600, topic 200, guidance 1500, fact 300, message 1000 characters. Everything but message bodies is one paragraph (whitespace, line breaks included, collapsed).
- Counts are capped because `getContext` loads every entry and topic into each conversation and at most 50 facts (verified first, then newest): 150 entries, 30 topics, 40 verified facts, which leaves at least 10 places for the senior's newest unverified facts.
- Memory reads are bounded through `agentMemory.by_household_verified` (`householdId`, `verifiedAt`): verified facts, and the newest unverified ones. `listMemory` returns `{ facts, olderUnverified }`: verified facts, the newest 50 unverified, and a count of the older ones (up to 500). A fact's duplicate check covers the verified facts and the newest 500 unverified ones.
- Adds de-duplicate (entry: category and name; topic: wording; fact: text; case-insensitive) and return `{ id, created, same, confirmed }`: an existing row is returned unchanged, with `same` saying whether its text equals what was sent, compared exactly (an entry's name, and its details when details were sent; a topic's wording and guidance); the caller decides whether to update it. Adding a fact the senior already stated verifies it (`confirmed`). Renaming onto another row's key is refused.
- Only an editor caregiver verifies (`verifyFact`, first verifier kept) or corrects (`correctFact`, which verifies and keeps the source) a fact.

Privacy: conversation summaries, question text and turns carry what the senior said, so caregivers can read them only when `households.shareTranscripts` is true. The digest reports topics and counts. `agent:*` functions require `SUNNY_AGENT_KEY`; the household always comes from the LiveKit participant metadata the token action wrote, never from the model.

| `phoneVerifications` | The one outstanding verification per member: `phone`, `codeHash` (HMAC bound to user and number, absent until the code exists), `sendError`, `sendErrorDetail`, `expiresAt` (10 minutes), `attempts` (5 wrong guesses lock it) | `by_household_user` (uniqueness), `by_expires` | `phone.ts`: `setMyPhone` replaces the row, `sendCode` stores the hash, `confirmMyPhone` deletes it on success, `sweepExpired` (hourly) |

Rules: the code is made inside the send action and never stored or scheduled in plaintext. `households.myPhoneStatus` (implemented in `phone.ts` and re-exported from `households.ts`) lets a client wait for the send (none, sending, sent, send_failed, expired) and returns only the caller's own pending number. A failed send stores a caregiver-safe `sendError` (generic, or "That number cannot receive texts.") and the raw text in `sendErrorDetail`, which no function returns. `expired` is computed from `Date.now()` inside the query, which Convex does not re-run as time passes, so a subscribed client should compare `expiresAt` with its own clock. Sends are rate limited per caregiver, per caregiver and number, and per day for each caregiver and household. Only verified numbers (`phoneVerifiedAt`) receive texts, and only allowed countries (`SMS_ALLOWED_COUNTRY_CODES`, default US/CA).

## Audit

`auditLog`: `actorUserId`, `actorKind`, `action`, `entity`, `entityId`, `detail`. Indexes `by_household`, `by_household_action` (the voice agent reads how an earlier family message went out). Written only by `lib/audit.ts`.

`agentFlags`: one row per voice agent flag that reached family: `reason`, `key`, `at`, `names`, `recipientUserIds`, `doseId` (the dose a medication-limit flag was about, for the correction when it is taken back), `conversationId`. Indexes `by_household_key_at` (the repeat check), `by_household_at` (the hourly cap). Written only by `lib/voiceRouting.ts`; every flag decision is also an `auditLog` row (`flag_caregiver`).

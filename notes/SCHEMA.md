# Shared State Schema (Convex)

How Sunny's Convex tables implement `notes/SPEC.md`. The source of truth is `sunny_backend/convex/schema.ts` (every field is commented there); this file explains what each table is for, who writes it, and the rules the code keeps because the database does not. Enums live in `convex/lib/validators.ts`. History of the move from Supabase: `notes/CONVEX_MIGRATION.md`. Background work: `notes/AGENT_RUNTIME.md`.

## Conventions

- **Instants** are epoch milliseconds (`number`), for example `windowStart`, `expiresAt`, `settledAt`. Convex's own `_creationTime` is also epoch ms, but the scheduler uses explicit `createdAt` where tests must drive the clock.
- **Household-local dates and times** are strings: `"YYYY-MM-DD"` and `"HH:MM"`. Schedules are stored in local terms so 8:00 stays 8:00 across DST; the instant is computed from the household's IANA region timezone (`lib/time.ts`, no dependency). Weekdays are ISO numbers, 1 = Monday.
- **User ids** are Clerk user ids (the identity's `subject`). A senior device is also a Clerk user, created at pairing with `public_metadata.sunny_kind = "device"`.
- **View shapes use `null`.** Results built for the apps (`calendar.dayView`, `listEvents`, `instances.today`, `confirmDueTask`) return `null` for an absent optional value, never a missing key. Raw document returns keep Convex's omitted-field shape.
- **Uniqueness is kept by code.** Convex has no unique constraints. The writing mutation looks the key up through an index first (serializable transactions make check-then-insert safe). Keys: one instance per task, local date and time; one join code per value; one connection per caregiver per household; one verification per member; one digest per household and local date (and so one digest chat post); one sync per event and connection; one `agentToolCalls` row per request and tool use id; one `eventNotices` row per event and date.
- **Actor model.** `actorKind` is `caregiver`, `senior_device`, `agent` or `system`. Every write path records who acted (`createdVia`, `confirmedVia`, audit rows). The household agent's actor also carries the caregiver it acts for (`onBehalfOf`) and its request (`requestId`): `actorUserId` returns that caregiver, so what the agent creates has `createdBy` = the requester and its audit rows have `actorUserId` = the requester and `detail.requestId`. The voice agent carries neither. Public functions resolve the caller through `lib/access.ts` (`requireReader`, `requireEditor`, `requirePrimary`, `requireSenior`) and reject device identities from every caregiver check. Backend-only work is an `internal*` function. The Python voice agent calls `agent:*` functions with `SUNNY_AGENT_KEY` as the first argument; it may pass `now`. Public functions never accept `now` from clients.
- **Deletes.** Events are soft deleted (`deletedAt`) so cancellations sync to Google. Tasks are hard deleted through `tasks.remove` / `purgeTaskData`, which also remove their instances and notifications. There is no household delete yet.
- **Audit.** `lib/audit.ts` writes `auditLog` rows from the mutations that change audited tables. It is called explicitly; nothing is automatic.

Rules:
- A caregiver belongs to at most one household: `households.create` and `redeemJoinCode` reject a caller who already has a `householdMembers` row ("invalid"), and the check runs before anything is inserted (a rejected redeem leaves the code unused). A caregiver removed by `removeMember` can then create or join another. The rule is enforced in code, not by an index, and older rows may still hold two memberships.
- A household always keeps at least one primary: the last primary cannot be demoted or removed.
- A device's `userId` is a Clerk user made at pairing. Re-pairing creates a new user, so a push token held by an orphaned user (no device row, no membership) may be taken over. Between caregivers a token moves to whoever registers it last (one phone, one token: the newest caregiver to sign in holds it, so an earlier caregiver whose sign-out could not unregister stops getting that household's pushes there). A paired device's token never moves, and a device never takes a live caregiver's token (`households.registerPushToken`).
- What takeover allows, and why it is acceptable: a caregiver who knew another caregiver's raw APNs token could move it to their own account. The token is never shown to other users, APNs still delivers only to the physical phone that owns it, the previous owner's rows then go to them by SMS (or not at all without a verified phone, as for anyone without the app), and nothing can be read through a token.
- `pairingNonce` and `pairedAt` support retrying a lost `/pair` response for 10 minutes. `listDevices` strips the nonce and `tokenHash`.
- A device token (`sunny_dev_` plus 32 random bytes, base64url) is made only in an action and stored only as its hash. Issuing a new one replaces the hash (at most 10 an hour); `households.revokeDeviceToken` (editors only, audited `revoke_device_token`) clears it and keeps the device paired; removing the device deletes the row. Either revokes the token at once.
- Removing a member drops their Google connections, links and pending syncs and revokes the grants.
- `backgroundPaused` is read by every workflow step, workpool job, the scheduler and the digest. Resuming re-pushes calendars (`households.update`).

## Device API

For senior surfaces that cannot hold a Clerk session (the iOS widget and Live Activity, the e-ink display firmware). Code: `deviceApi.ts`, `lib/deviceToken.ts`, `lib/deviceState.ts`, `lib/deviceWording.ts`, `lib/escalation.ts`.

- A signed-in senior device calls `deviceApi.issueToken` (action, audited `issue_device_token` without the token) and gets `{ deviceToken }` once.
- Every request sends `Authorization: Bearer <deviceToken>`; every response has `Cache-Control: no-store`. A missing, malformed or unknown token is 401 with one fixed body; firmware should stop polling and ask to be paired again. While the global failed-authentication bucket is empty (someone sent 60 bad tokens in the last minute), a revoked device gets 429 instead of 401, so firmware should also give up and re-pair after repeated 429s on the same token. Every route, an unexpected 500 included, answers with no-store JSON.
- `GET /device/state`: the device state with `ETag: "<version>"`; `If-None-Match` with that tag gets 304 and no body.
- `POST /device/confirm` `{ instanceId, pressedAgoMs, via }` (`button`, `widget`, `live_activity`, `phone_app`): `instances.confirmPressedInstance` as the device; 200 `{ status: "confirmed" | "rejected", reason, state }`. The state is read after the press in its own query; if that fails the press still stands and `state` is null (the device then calls GET). Another household's instance is answered exactly like a deleted one. Bad body or id: 400. `pressedAgoMs` is 0 to 7 days; bodies are at most 4096 characters.
- Audited refusals (`press_not_applied`, actor the device, `transport: device_api`): everything `confirmPressedInstance` refuses (a deleted instance, too early, outside the replay window, made before a take-back), what the device API refuses before it (an unreadable body, a bad instance id, a press over 7 days old), and another household's instance, which the core refuses with its household check (the one every confirm goes through) and the device API answers like a deleted one and records in the device's own household without that id; the raw id text is never stored. At most 20 refusal rows an hour per device, the core's included; past that the answer is the same and no row is written.
- A confirm through the device API is a device confirm like the app's: state `confirmed`, `confirmedBy` the device's user, so a caregiver's reopen stamps `confirmTakenBackAt` and the phone app's Undo (`undoPressedTask`, same device user) can take it back. The device API itself has no undo: the display and the widget offer none (`notes/SPEC.md`).
- `PUT /device/info` `{ screen?: { width, height, greys }, firmware? }`: width and height whole numbers 1 to 10000, greys 2 to 256, firmware 1 to 40 characters after trimming; any other field is 400; 204.
- Rate limits: 120 requests a minute per device; failed authentications spend a global bucket (60 a minute) and a per-IP bucket (10 a minute) and get 429 with `Retry-After` once either is empty. A valid token is never refused because of other callers' failures.
- The device state (`lib/deviceState.ts`, also the Convex query `deviceApi.state` for a Clerk-signed-in device, the identical object): `version` (FNV-1a 64 of the content, without `generatedAt`; the ETag), `displayVersion` (the hash of only what is drawn: dates, header, now, done, nextUp, rows, rowsHidden; a panel repaints only when it changes, not when a cue time passes), `generatedAt`, `seniorPreferredName`, `timezone`, `utcOffsetMinutes`, `localDate`, `header`, `dateLabel`, `fullDate`, `now` (the Now card; never "all done" while a task today is missed), `done` (the task a Done press confirms: the phone's rule, so possibly early), `nextUp`, `rows` and `rowsHidden` (the Today page; marks `now`, `done`, `missed` (dimmed) or `none`, as the app draws them), `cues` (sentence, prompts sent, snooze, and `promptTimes`: the instants in the next 24 hours at which the escalation policy will prompt, from the scheduler's own timing code) and `tuning` (poll intervals and carousel). Absent values are null.

Every reader (status, limits, repeated use, context, digest facts) leaves undone rows out |

State machine (`instanceState`):

```
upcoming --(window_start)--> due --(caregiver alert step fires)--> escalated
   |                          |                                      |
   +--(confirm, <=60 min early)+--(confirm)--> confirmed <--(confirm)-+
                              |                                      |
                              +--(window_end, unconfirmed)--> missed <+
due / escalated / missed --(caregiver marks done)--> resolved
missed --(senior confirms late)--> confirmed (late = confirmedAt > windowEnd)
confirmed --(the same senior device undoes, <=60 s after the server recorded it)--> the state before the confirm
confirmed / resolved --(editor caregiver reopens, confirmed today)--> upcoming | due | escalated | missed, by the clock
```

Rules:
- `instances.ts` is the single write path for every surface. A senior device or the agent produces `confirmed`; a caregiver produces `resolved` with `confirmedVia = caregiver`. Confirming an already confirmed or resolved instance returns the original result. The audit detail of a confirm says how it arrived: `transport` is `app` for the app's mutations and `device_api` for the HTTP device API (unset for the voice agent). `confirmDueTask(household, via, label?)` is what the Done button, widget and voice call; it returns a status (`confirmed`, `already_done`, `nothing_due`, `not_found`, `ambiguous`, `not_due_yet`), so the double-dose guard lives in one place.
- Every confirm records the state and snooze it replaced in `resolvedFromState` and `resolvedFromSnoozedUntil` (device, agent and caregiver alike; the names date from the caregiver resolve). **Senior undo** (`instances.undoPressedTask`, senior devices only): the phone shows Undo for 30 seconds; the server allows `SENIOR_UNDO_MS` (60 s) so a slow network never refuses a press the senior was offered. It needs state `confirmed`, `confirmedBy` equal to this device's user id (not another device's, the voice agent's or a caregiver's confirm) and `now - (confirmReceivedAt ?? confirmedAt) <= SENIOR_UNDO_MS` (measured from when the server recorded the confirm, because an offline press carries an earlier `confirmedAt`). It also needs the task to still run (same test as reopen; else `too_late`). Measured from `confirmedAt` for a press that took 1 to 5 minutes to arrive (no `confirmReceivedAt`), such a press lands already past 60 s; accepted, the phone's Undo has expired by then. It restores the prior state (by the clock, as a reopen does, when none was recorded), the snooze, and clears the confirmation fields; audited as a `state_change` with `undo: true`. Any failed condition returns `{ status: "too_late" }` and changes nothing; it never throws for a late tap (only `forbidden`: not a senior device, or another household's instance). The caregiver's own 30 s `undoResolve` only applies to `resolved`, so it cannot touch a device's confirm. **Caregiver reopen** (`instances.reopenTaskInstance`, editors only; the home display has no undo): allowed when state is `confirmed` or `resolved` (whoever confirmed it) and either the household-local date of `confirmedAt` or the instance's own `localDate` is today's (the second covers a 00:30 task confirmed at 23:45 the evening before; `invalid` otherwise; the task must still run, i.e. exist, be active and still be timed at that time or anytime to match, else `invalid` "This task is no longer on the schedule." because deactivating or editing a task deletes only its open instances;  viewers, devices and other households are `forbidden`). The new state is by the clock (`lib/confirmRule.reopenedState`): before `windowStart` `upcoming`; inside the window the recorded prior state if it was `due` or `escalated`, else `due`; at or after `windowEnd` `missed`. Anytime instances never escalate, so inside their window they reopen as `due`, and after it as `missed`. The confirmation fields and `resolvedFrom*` are cleared; the note and any claim are kept; no snooze is restored. Undo and a reopen of a device confirm set `confirmTakenBackAt` (to `now`, or to the offline tap time): `confirmInstance` refuses (`invalid`) a press carrying an age whose press time (`now` minus the age) is at or before it, so a press the device's durable queue still holds after its acknowledgement was lost cannot confirm the task again; through `confirmPressedTask` this is `{ status: "rejected" }` with the usual `press_not_applied` audit row. A press without an age (the home display's live confirm, voice, a caregiver's Mark done) is not checked against the stamp, since it is by definition made now; a press made after the take-back confirms as usual. A reopen stamps only a device or voice confirm (`confirmed`), not a caregiver's `resolved`, because nothing was taken back from the senior. An Undo tapped offline carries `undoneAgoMs`: the 60 s rule is judged at the tap time and the stamp is the tap time clamped to between `confirmedAt` and now, so a Done pressed after the Undo tap still applies when delivered later. A caregiver alert skipped as `instance_closed` while the instance was done is not re-sent after an undo or reopen. The ladder just continues: steps in `firedSteps` are not repeated and unfired steps fire when due (a reopen late in the window can fire an overdue step on the next tick; only the latest of each kind notifies). Audited as a `state_change` with `reopen: true` and the previous `confirmedAt`, `confirmedBy`, `confirmedVia` (the previous state is `from`). The day view's `reopenable` flag (`TodayEntry`) is the same time, state and task-still-runs rule (`caregiverCanReopen` and `taskStillRuns`), so the app never offers a Reopen that will fail; the role is the mutation's check.
- The scheduler tick (`scheduler.ts`, every minute) fans out one `tickHousehold` per household: expand today and tomorrow (idempotent through the `by_task_date_time` lookup; a window that already closed is skipped unless the task existed when it opened), open windows, fire each due escalation step once (recorded in `firedSteps`; when several steps of one kind come due together only the latest is sent and the rest record `notified: false`; a caregiver alert, the legacy `alert_on_call` included, goes to every caregiver of the household), mark instances with a fired caregiver alert `escalated`, and close windows to `missed`. Offsets count from the later of `windowStart` and `createdAt`. Snoozes defer senior prompts only; `skipIfClaimed` steps stop once claimed.
- Editing a task's schedule or the household timezone deletes future `upcoming` instances and re-expands; deactivating a task removes its open instances.
- Seeded policies: **Medication** (0 min prompt, 15 min reprompt, 30 min alert to every caregiver at once; anyone who may claim can claim it; the window closing marks it missed) and **Prompt only** (0 min prompt). There is no on-call caregiver and no separate 45 min step (2026-11-14). A caregiver may claim a due task before 30 min; the alert still goes to everyone (a claim is not a dose). A ladder with two caregiver alerts (one not yet migrated, or a custom one) alerts everyone at each step, the later one only while still due (a `skipIfClaimed` step is skipped once claimed, and its text adds "No one has claimed it yet.").
- No on-call caregiver (2026-11-14): `migrations.removeOnCall` (internal; run with `npx convex run migrations:removeOnCall`; idempotent, one page of households per run, scheduling itself for the next and logging each page's counts) clears `households.onCallUserId` and rewrites each `alert_on_call` step to `alert_all_caregivers` (same id, offset and `skipIfClaimed`), dropping a later `alert_all_caregivers` step with `skipIfClaimed` that only repeated it for the unclaimed case, so the old default ladder ends exactly on the new one. A household with an open (due or escalated) instance that has already fired an `alert_on_call` step keeps its ladder for now (its `onCallUserId` is still cleared) and is counted as `deferred`, because that instance may still need the later all-caregivers step; when `deferred` is not zero, run the command again once those windows have closed (at most a day). Once it has run on every deployment, delete `households.onCallUserId` from `schema.ts` and the `alert_on_call` literal from `lib/validators.ts`. Seeded policies cannot be deleted or re-keyed. A task with no policy shows on the surfaces and in the digest but never notifies, so `createTaskCore` (used by `tasks.create` and the agent's `add_task`) assigns a default when no `escalationPolicyId` is given: the household's `medication` policy for `medication` tasks, `prompt_only` for every other type (looked up by `systemKey`; an explicit policy wins; a household missing the seeded policy still creates the task with none). Changing a task's type across the medication boundary (to or from `medication`), in `tasks.update` or the agent's `update_task`, switches the policy to the new type's default when the current policy is one of those two seeded policies; a custom policy is left alone, and a policy given in the same update wins. To fix older tasks with no policy run once: `npx convex run tasks:backfillDefaultPolicies` (no arguments; it also re-assigns tasks whose policy a caregiver deliberately cleared). Senior reminders use the prompt-only policy, found by `systemKey`, so renaming is safe.
- Policy `steps` are embedded. Instances record fired steps by step id, so editing the ladder never makes a step look fired or unfired.

## Notifications and delivery

| Table | Purpose and key fields | Indexes | Written by |
| --- | --- | --- | --- |
| `notificationOutbox` | The only place notifications are queued. One recipient per row: `recipientDeviceId` (APNs) or `recipientUserId` (a caregiver: APNs when they have a push token, else SMS). `kind` (`senior_prompt`, `caregiver_alert`, `event_notice`, `digest`, `agent_flag` (the voice agent asking a caregiver to look in; `payload.reason`, `payload.flaggedAt`), `family_message` (a message the senior dictated to family)), `title`, `body`, `payload` (a digest row's `pushTitle` is the push title, `title` stays the SMS's), `state` (`pending`, `sent`, `skipped`, `failed`), `channel` (set only when sent: what actually delivered it), `settledAt`, `attempts`, `attemptStartedAt` (lease), `detail` (skip reason or internal error, never returned to clients), `pushState` (a caregiver push with a text to fall back on: `retrying` after a retryable push failure, `gave_up` once the push retries ran out and the row was enqueued again to be texted) | `by_recipient_kind` (reply-to-claim), `by_recipient_device`, `by_task_instance` (cascade on instance delete), `by_household`, `by_state` | Inserted only through `insertNotification` in `lib/delivery.ts` (scheduler, event notices, digest, `lib/voiceRouting.ts` for agent flags and family messages); settled by `delivery.ts` |
| `smsInbound` | Inbound texts already handled, by Twilio `MessageSid`, with the stored reply, so a webhook retry claims nothing twice | `by_sid`, `by_expires` | `sms.ts`; swept hourly |

Rules:
- A row leaves `pending` once. Recipient, membership and content are re-checked at send time, so a stale or unreachable row is `skipped` with the reason in `detail`.
- Push first for caregivers (`lib/delivery.ts`): a member row goes by APNs when the member's user has at least one `pushTokens` row (the caregiver app with notifications on), otherwise by SMS exactly as before. The rule: a caregiver who would have been texted before push existed never ends up with nothing. When APNs is not configured, or takes none of the tokens with nothing worth retrying (every token unregistered, which deletes it, or refused for good), the same row is sent as the member's SMS in the same run, so it settles with `channel` `sms`. A retryable APNs failure is retried, not texted, and marks the row `pushState: "retrying"`; when the workpool's retries run out and the member has a verified phone, `delivery.onDeliveryComplete` sets `gave_up` and enqueues the row once more, and its route is then the SMS (`lib/delivery.ts` `textAfterPushGaveUp`), once per row. Without a verified phone a push that cannot be delivered ends `skipped` (`tokens_unregistered`), `failed`, or pending while APNs is not configured, as a device push does. Pushes carry data `notification_id`, `kind`, `household_id` and `task_instance_id` (when there is one); `caregiver_alert` and `agent_flag` to caregivers and `senior_prompt` to devices are time-sensitive; a `caregiver_alert` to a primary or member has the `caregiver_alert` category ("I'm on it"), a viewer's has none; the collapse id is the task instance (`lib/apnsPayload.ts`).
- Reachable (who a flag, a family message or the digest is queued for): a caregiver with a verified phone or at least one push token (`isReachableMember`).
- `attempts` is capped (`MAX_ATTEMPTS`) so the sweeper never loops on one row; `attemptStartedAt` is a 5-minute lease the sweeper respects. The text after a push gave up shares the row's budget, so a row that reaches the bound is failed, not texted.
- `agent_flag` and `family_message` rows go to caregivers like any member row and their texts never carry the "Reply 1" claim hint (they are not tied to a task); a "1" texted back after one of them claims nothing. Rows are queued only for reachable caregivers: an `agent_flag` goes to every reachable caregiver at once (there is no on-call caregiver); with nobody reachable nothing is queued, the decision is audited and the voice agent says family could not be reached. Only an identical event repeats: a flag whose key (the model's reason plus its detail text; for a medication limit or repeated use, the reason and the task) went out within 10 minutes is not sent again (repeated as-needed use: once a week), and that decision is audited too. At most 12 symptom, money and scam flags per household per hour (distress, help_requested, medication limits, repeated use and dose corrections are never capped); at most 10 senior messages per hour; an identical senior message within 2 minutes is not sent again, and the agent says how the first one went. A "1" texted back after a flag or family message gets "Thanks. Nothing needs claiming for that message." Flag text is at most two sentences and 240 characters, with runs of 6 or more digits removed. A timed-out text is retried only for `caregiver_alert` and `agent_flag`.
- Only tokens APNs reports unregistered are deleted from `pushTokens`.

Rules for the caregiver write path (`profile.ts`):
- Two front doors, one core: the About tab's mutations and the household agent's knowledge tools (`get_knowledge`, `add_knowledge`, `update_knowledge`, `remove_knowledge`, `lib/agentSetupTools.ts`) call the same exported cores (`addEntryCore`, `updateEntryCore`, `removeEntryCore`, `listTopicsCore`, `addTopicCore`, `updateTopicCore`, `removeTopicCore`, `listMemoryCore`, `addFactCore`, `verifyFactCore`, `correctFactCore`, `removeFactCore`), so every rule below holds for both. A chat change is recorded under the requesting caregiver (`createdBy`, `verifiedBy`, the audit row's user) with the request id in the audit detail.
- Editors (primary, member) write. All four lists are caregiver only (`requireCaregiverReader` in `lib/access.ts`: any role, never a paired device), since what they hold is written about the senior and nothing on the senior's screens uses them. `listMessages` returns `mine` for the caller's own messages and no member ids. Every change writes an `auditLog` row (`lifeProfileEntry`, `sensitiveTopic`, `agentMemory`, `familyMessage`); an update's or correction's row also holds the previous text (`detail.previous`), so a replaced value can be recovered. `requireCaregiverReader` (like every caregiver check) refuses a device by its token claim or by a `devices` row.
- Text is trimmed and capped: name 120, details 600, topic 200, guidance 1500, fact 300, message 1000 characters. Everything but message bodies is one paragraph (whitespace, line breaks included, collapsed).
- Counts are capped because `getContext` loads every entry and topic into each conversation and at most 50 facts (verified first, then newest): 150 entries, 30 topics, 40 verified facts, which leaves at least 10 places for the senior's newest unverified facts.
- Memory reads are bounded through `agentMemory.by_household_verified` (`householdId`, `verifiedAt`): verified facts, and the newest unverified ones. `listMemory` returns `{ facts, olderUnverified }`: verified facts, the newest 50 unverified, and a count of the older ones (up to 500). A fact's duplicate check covers the verified facts and the newest 500 unverified ones.
- Adds de-duplicate (entry: category and name; topic: wording; fact: text; case-insensitive) and return `{ id, created, same, confirmed }`: an existing row is returned unchanged, with `same` saying whether its text equals what was sent, compared exactly (an entry's name, and its details when details were sent; a topic's wording and guidance); the caller decides whether to update it. Adding a fact the senior already stated verifies it (`confirmed`). Renaming onto another row's key is refused.
- Only an editor caregiver verifies (`verifyFact`, first verifier kept) or corrects (`correctFact`, which verifies and keeps the source) a fact.

Privacy: conversation summaries, question text and turns carry what the senior said, so caregivers can read them only when `households.shareTranscripts` is true. The digest reports topics and counts. `agent:*` functions require `SUNNY_AGENT_KEY`; the household always comes from the LiveKit participant metadata the token action wrote, never from the model.

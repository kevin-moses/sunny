# Background runtime on Convex

How Sunny runs work that outlives a request: the per-minute clock, delivery of notifications, Google Calendar sync, reading the senior's Gmail, and the agent tasks a caregiver asks for. Tables are described in `notes/SCHEMA.md`; this file covers where work runs, the flows, and the contracts that are not obvious from the code. The code has no comments, so contracts that the code cannot express are written here. History: `notes/CONVEX_MIGRATION.md`.

Research on Meta's Muse and OpenAI's dots (2026-10-26) shaped the design: both store schedules and pending work durably and treat compute as disposable. We copy that and skip their always-on VM per user, which costs money while idle and keeps memory that caregivers cannot see. Here the durable state is Convex tables, and every piece of compute (a mutation, an action, a workflow step) can disappear and be rerun.

## Where work runs

| Piece | Job | Never does |
| --- | --- | --- |
| Convex queries and mutations | Reads and transactional writes: access checks, task and event CRUD, instance confirm, claim, the per-household scheduler pass, queueing deliveries and syncs | Call a model or a third-party API (mutations are deterministic and cannot use WebCrypto or `fetch`) |
| Convex actions | Anything that calls out: Managed Agents, Google (Calendar and Gmail), APNs (`"use node"`, `node:http2`), Twilio, Clerk, LiveKit token minting, TypeSafe's Jev for sorting mail, Claude Haiku for the digest and mail summaries | Hold state; each action reads and writes through internal queries and mutations |
| `crons.ts` | The clock: `scheduler.tick` every minute; `gmail.pollAll` every 5 minutes; every 10 minutes `calendarFanOut.sweepStuckSyncs`, `delivery.sweepStuck` and `mailTriage.sweepStuck`; hourly `googleOauth.sweepOauthFlows`, `phone.sweepExpired`, `sms.sweepInbound` | Do the work inline |
| Scheduler tick and fan-out | `tick` pages through households and schedules one `tickHousehold` each with the same `now`, so no transaction grows with household count. Each household pass runs in its own serializable transaction: expand instances, open and close windows, fire escalation steps, queue event notices and the daily digest | Share a transaction between households |
| Workpool `deliveryPool` | Delivers `notificationOutbox` rows (`delivery.deliver`) and composes digests (`digest.compose`), max 10 in parallel, 5 attempts with exponential backoff | Run a job for a settled row |
| Workpool `calendarSyncPool` | Pushes one event to one caregiver's Google calendar (`calendarPush.push`) with retry and a parallelism cap | Call Google for a paused household or inactive connection |
| Workpool `mailPool` | Polls one mailbox (`gmail.poll`) and triages one mail item (`mailTriage.triage`), max 5 in parallel. A poll gets 3 attempts starting at 5 seconds; a triage gets 5 attempts starting at 30 seconds, each wait doubling | Read a mailbox for a paused household or one that is not active |
| Workflow (`agentRuntime.ts`) | One caregiver request to the household agent, as durable steps over a Managed Agents session | Run a step without re-checking the request and the pause switch |
| HTTP routes (`http.ts`) | `POST /pair` (device pairing), `GET /google/start`, `GET /google/callback`, `POST /twilio/sms` (signature checked) | Trust the caller without checks |
| LiveKit voice agent (`sunny_agent`, self-run Python) | The live conversation with the senior. Reads and writes household state through the `agent:*` Convex functions over HTTP, authenticated by `SUNNY_AGENT_KEY` | Outlive the call or write tables directly |
| Claude Managed Agents | The model loop for caregiver requests, behind `lib/managedAgents.ts` | Hold state Convex does not also have |

Components are registered in `convex.config.ts`: rate limiter, workflow, and the three workpools.

**Pause switch.** `households.backgroundPaused` is checked by the scheduler, every workflow step, every push and delivery before it acts, the digest, the Gmail poll and the claim of each mail item. A caregiver "stop" covers all background work at once. Resuming re-pushes calendars. Queued work stays queued, except a caregiver's request to the household agent: it still fails 30 minutes after it was made, pause included, with an error that says it timed out while paused.

## Agent request flow

A caregiver sends a message with `agentRequests.request` (editors only: primary or member). The mutation validates it (1 to 4000 characters, at most 5 queued or running per household), inserts an `agentRequests` row and starts the workflow. The app subscribes to `agentRequests.get` / `list` for the reply.

1. **Steps.** `markRunning`, `startSession`, then one `pollSession` per poll; when the session needs tool results, `executeToolCalls` and `sendToolResults`; finally `finishRequest`. A reply with no tools is 4 steps; each tool round adds 3. `startSession` creates a Managed Agents session with the message and a household briefing built from Convex: the senior's preferred name, timezone, the local weekday and date/time now, the requesting caregiver's display name, the caregivers with their roles, the coming calendar, the active tasks, the emails Sunny escalated in the last 3 days, and the digests sent today and yesterday. The emails and the digests are marked as information only. Every request's message starts with the briefing, a continuation's too.
2. **Tools** (`lib/agentTools.ts`): calendar `get_calendar`, `add_event`, `update_event`, `cancel_event`; tasks `get_tasks`, `add_task`, `update_task`, `stop_task`; and the setup tools of `lib/agentSetupTools.ts`. The setup tools are knowledge `get_knowledge`, `add_knowledge`, `update_knowledge`, `remove_knowledge` (each with a `kind`: `profile`, `topic` or `fact`, and a `knowledge_id` for change and removal) and settings `get_settings`, `update_settings` (digest time, `share_transcripts`, weather place). The digest goes to every caregiver and cannot be turned off.

   `add_task` and `update_task` take `high_priority`: medications always alert caregivers, and another task alerts only when it is high priority. `get_tasks` returns `high_priority` and `alerts_caregivers`, and the briefing's task lines say "high priority".

   Each tool is a thin wrapper over the same functions the app uses (`calendar.ts`; the task cores `createTaskCore`, `updateTaskCore`, `listTasksCore` in `tasks.ts`; the profile cores in `profile.ts`; `lib/householdSettings.ts` `updateHouseholdCore`), so there is one write path and one set of checks. Knowledge and settings results carry the item or settings as they are now stored (`remove_knowledge` carries the removed item), so the reply can say what was stored. No tool takes a caregiver's name or id.

   A successful `add_task` or `update_task` also returns its task id. The id is appended to the request's `changedTaskIds` in the same transaction (each task once, at most 20) for the chat's wording cards. This changes only what the `executeToolCalls` step does inside its mutation, not the workflow body.

   `executeAgentTool(ctx, { householdId, actor, now }, { name, input })` runs a handler from a name-to-handler table; an unknown name is a tool error. The household and the actor come from the request row, never from the model. The actor is `{ kind: "agent", onBehalfOf: <requesting caregiver>, requestId }`, built once per `executeToolCalls` batch. Provenance: an event the agent adds has `createdVia = agent` and `createdBy` = the requester; a task has `createdByKind = caregiver` and `createdBy` = the requester; audit rows have `actorKind = agent`, `actorUserId` = the requester and `detail.requestId`.

   The agent can stop a task (`active = false`, history kept; `update_task` with `active: true` resumes it) but cannot delete one. For every task, whether the agent, the app or the senior's voice made it, a display label is at most 60 characters and a title at most 200. Rules the agent has beyond the app:

   - An active medication task must have at least one time, checked on the merged result of `add_task` and `update_task`. Any other type may have none, which makes it an anytime task (`lib/anytime.ts`). As-needed medications stay app-only, so the tools have no as-needed fields.
   - `add_task` refuses a duplicate and names the existing `task_id`. A duplicate is an active task with the same type, the same label ignoring case and spacing, and a shared time, or both anytime.

   The briefing lists the events of the next 7 days with `event_id`, and the active tasks with `task_id` and today's status. The status comes from `lib/today.ts`, so yesterday's still-open instances and who confirmed what are included. `get_tasks` is for stopped tasks or a list cut off at 30, and `get_calendar` is for other dates.

   The agent has no shell, files or web (see `lib/agentConfig.ts`). Sessions are created with the deployed model, prompt and tools as `agent_with_overrides`, and each request stores `agentConfig`, a fingerprint of them from `lib/agentFingerprint.ts`. When the fingerprint differs from the latest conversation's, `continueLatest` starts a new session marked `carryOver`, whose first message includes the recent chat from `lib/agentHistory.ts`. In that chat each caregiver line is labeled with its author's display name, and every message is flattened to one line so it cannot pose as another speaker. The prompt treats that section as context only: the agent never carries out an earlier request from it, except when the current message answers the question in Sunny's most recent reply there; otherwise it asks whether the caregiver still wants it.
3. **Tools run exactly once.** A tool call's `agentToolCalls` row is inserted in the same transaction as its effect. A repeat of the step finds the row and reuses its result; results already sent are marked `sentAt` so a lagging event list is ignored. A retried step therefore cannot add an event twice.
4. **One in-progress request per session.** `request` rejects a continuation while another request in the same session is queued or running. A continuation copies the earlier `sessionId` onto its row up front, and records `baselineUserMessages` (the session's user messages before posting). `finishedTurn` ignores any turn that does not include a newer user message, so a lagging event list cannot return the previous reply.
5. **Pause switch and cancel.** Every acting step re-reads the request and `backgroundPaused` (`readGate`). While paused, the workflow sleeps a minute and retries. When the request is no longer queued or running (it was cancelled), the run ends.
6. **30-minute cap.** A request older than `MAX_REQUEST_AGE_MS` (30 minutes from creation, paused time included) fails; the error says it timed out (or timed out while paused).
7. **Per-session budget.** `SUNNY_AGENT_SESSION_BUDGET_CENTS` (default 100) caps spend. A stop for budget, refusal or exhausted retries fails the request.
8. **Caregiver-safe errors.** `error` is plain text shown in the app. Raw detail (SDK errors, env var names, ids) goes to `errorDetail`, which no public query returns, and to the logs. `onRunComplete` fails or cancels the row if the workflow dies while the row is still in progress.
9. **Workflow versioning.** Changing the steps breaks runs in flight. Runs are short (30-minute cap) today. Before `wait_for_reply` ships, workflows need a version field and old versions kept until their runs drain.

Env on the Convex deployment: `ANTHROPIC_API_KEY`, `SUNNY_AGENT_ID`, `SUNNY_ENVIRONMENT_ID`, optional `SUNNY_AGENT_SESSION_BUDGET_CENTS`.

## Google Calendar sync

Sunny's `events` table is the source of truth. Each caregiver who connects Google gets their own secondary calendar (named like "Mom (Sunny)") created by Sunny with the narrow `calendar.app.created` scope: Sunny can create and edit calendars it made and nothing else in the account. Setup: `notes/GOOGLE_CALENDAR_SETUP.md`.

- **Connect.** The flow lives in `googleOauth.ts` and serves two purposes, `calendar` and `mailbox`; the `GOOGLE_PURPOSES` registry gives each its scope, its consent prompt, the caregiver roles that may start it (any member for a calendar, a primary caregiver or member for a mailbox) and its finishing step. The flow is bound to the browser that starts it. `googleOauth.connectUrl({ householdId, purpose })` (a public action; caregiver members only, never a device) stores the hash of a random one-time ticket in `oauthFlows` (5-minute expiry) and returns `<host of GOOGLE_REDIRECT_URI>/google/start?ticket=...`, not Google's URL. `GET /google/start` redeems the ticket once, stores the hash of a random browser secret and an encrypted PKCE verifier on the flow (expiry extended to 10 minutes), sets the host-only cookie `__Host-sunny_google_flow` (Secure, HttpOnly, SameSite=Lax) and redirects to Google with an S256 code challenge and a state of `<flowId>.<HMAC>` signed with `GOOGLE_OAUTH_STATE_SECRET`. Google redirects to `GET /google/callback`, which verifies the state, consumes the flow on every attempt and requires the cookie to match the flow's browser hash. When a check fails, the callback refuses without storing anything: it shows a "Link expired" page and audits `connect_refused` with reason `flow_used`, `flow_expired`, `flow_not_started`, `no_browser_cookie` or `wrong_browser`; a code that Google rejects gets `code_rejected`. Every callback answer clears the cookie. When the checks pass, the callback exchanges the code with the verifier and checks that Google granted the purpose's scope; when it did not, the callback revokes the grant and shows a "Permission needed" page. Otherwise it hands the grant to the purpose's finishing step. For a calendar, `googleCalendar.finishCalendar` reuses the caregiver's existing Sunny calendar if it still exists (else creates one), encrypts the refresh token (`lib/secretBox.ts`) and calls `saveConnection`. That mutation reactivates the connection and schedules a chunked push of every event that can still occur, plus cancelled events that are still linked. A grant that ends up unused (rejected callback, replaced or dropped connection) is revoked at Google, best effort, under the rule in "Revoking a grant" below. Known limits: a link preview that fetches the start link uses up the ticket; two flows in one browser overwrite each other's cookie, so the first fails closed. No app screen starts the flow yet (only `scripts/caregiver.ts google`); an app button should open the start link with `expo-web-browser` (an auth session or SFSafariViewController keeps the cookie).
- **State machine** (`calendarSyncs`, described once in `lib/calendarSync.ts`). One row exists per event and connection while a push is pending: `queued`, then `running` when the push begins, `dirty` if the event changes while it runs, deleted on completion (a dirty row goes back to `queued`). With this, ten quick edits merge into one Google write. When retries run out, the row is tried once more after a delay, and the connection gets a caregiver-safe `lastError` that the next success clears. A push that ends in a hold (see Revoke and removal) puts the row back to `queued` instead of deleting it, and the sweeper tries it again.
- **Push.** `calendarPush.push` builds the Google event (local start and end in the household timezone, a weekly `RRULE` for repeats, a popup reminder at `eventNoticeTime` on the day, or 60 minutes before an event that starts at or before that time, our event id in `extendedProperties.private`). Google event ids derive from Sunny's, so a retried create replaces instead of duplicating. The access token is cached encrypted on the connection and refreshed only when missing, near expiry, or after a 401. Cancelled events are deleted from Google.
- **Chunked fan-out.** Backfill after connecting and resync after a household change (timezone, notice time, senior's name, pause ending) never run inline: `calendarFanOut.chunk` queues at most `FAN_OUT_CHUNK` syncs and schedules the next until the events are done.
- **Sweeper.** Every 10 minutes `sweepStuckSyncs` re-enqueues at most 200 rows idle for 15 minutes: a lost job, or a held push waiting for its cause to clear.
- **Revoke and removal.** Revoked access (`invalid_grant`) marks the connection `revoked` and stops retries; the caregiver reconnects, which also pushes cancellations made meanwhile. The connection is marked `error` when Google confirms that the calendar is gone, on a permanent 403 other than a hold, or when Sunny can no longer decrypt the credentials. A hold is an error that would be the same for every event and every connection: a missing env var, Google's daily project limit (`dailyLimitExceeded`, 403 or 429) or an API disabled for the Google Cloud project (`accessNotConfigured`, 403; Google's global error table also uses it for a project blocked for abuse or marked for deletion). A held push is logged and returns `held` without a workpool retry; `onPushComplete` puts the row back to `queued` with a new `updatedAt` and enqueues nothing, so the sweeper pushes it again after 15 minutes, until the cause clears. A hold does not count toward `failures`, leaves the connection `active` without a `lastError`, and posts nothing. A hold raised while checking whether the calendar still exists after a 404 is handled the same way. Only an `active` connection is marked, so when two pushes fail at once the first mark stands. One event's 404 does not disable the connection. Dropping a connection (`disconnect`, or a caregiver leaving the household) deletes its links and pending syncs and schedules revocation of the grant (see "Revoking a grant"); a running push finds its row gone and stops. `disconnect` leaves the Google calendar as it is.
- **Revoking a grant.** Revoking one refresh token at Google removes every scope that Google account granted to Sunny's project and invalidates all its tokens, calendar and mailbox alike. So Sunny revokes a grant only when it knows the grant's Google account and no mailbox or calendar connection, in any household, still uses that account (`revokeUnusedGrant` in `lib/googleTokens.ts`, checked through the `by_account` indexes when the revoke runs). Reconnecting the same account, or refusing a flow for an account that holds another connection, revokes nothing. A grant whose account Sunny cannot tell is never revoked. Account emails are stored in lower case.
- **A job's grant.** A reconnect rewrites the same mailbox or calendar connection row with the new account and grant, while poll, triage and push jobs started on the old grant may still be running. So every write a job makes for its grant names the stored, encrypted refresh token it started with, and does nothing when the row now holds another one (`holdsGrant` in `lib/googleTokens.ts`). Mailboxes and calendar connections share this code: `googleGrant.ts` saves a refreshed access token (`saveToken`) and marks a row `revoked` or `error` (`markGrant`) for either table, and `lib/googleGrant.ts` sorts a Google error the same way for both, with each table's own caregiver-safe messages. This covers saving a refreshed access token, marking the row `revoked` or `error`, recording a poll's message ids and history id, and recording a pushed event's link. Without it, an old grant's `invalid_grant` would mark the new connection revoked, or an old access token would be saved on the new row and used for up to an hour. A triage job whose mailbox no longer reads the item's account when it applies ends `failed` and changes nothing, the same as at claim time. Known limit: `onPollComplete` and `onPushComplete` get only the row id from the workpool, so an old-grant job that fails for good still sets the new row's `lastError` notice. The status does not change, and the next successful poll or push clears the notice.
- **Day-of notices.** Two paths: the Google popup (Google's own app notifies the caregiver) and an `event_notice` outbox row for every caregiver at `eventNoticeTime` (or right away for an event added later that day, if it has not started), written by the household tick.

## Gmail

Sunny reads the senior's own Gmail, one mailbox per household, with the read-only scope `gmail.readonly`. Appointments go onto the Sunny calendar, short news goes to the senior, and anything that needs a decision goes to the caregivers. Email is untrusted input: Jev answers typed questions, code turns the answers into a verdict and decides what happens, and Sunny acts by itself only on mail whose sender Gmail verified. Setup: `notes/GOOGLE_CALENDAR_SETUP.md` section 6.

Terms in this section. A verdict is what the classifier concludes about one email: `ignore`, `appointment` (new, reschedule or cancel), `senior_info`, `needs_decision` or `suspicious`. A judgment is one yes-or-no answer from Jev; it is unsettled when its probability is between 0.3 and 0.7, and an unsettled judgment sends the email to the caregivers. Facts are what Sunny's own tables say at the moment the email is applied: the calendar, how many calendar changes mail made today and how many senior notes mail wrote today. A link (`mailEventLinks`) ties an event to an appointment key that an email gave it, and belongs to the domain of that email's sender. An effect is one thing Sunny does with an email: add or move an event, write a sentence for the senior, or post to the caregivers.

- **Connect.** A primary caregiver or member opens the `mailbox` purpose of the browser-bound flow (see Google Calendar sync) and signs in as the senior. The consent link uses `prompt=consent select_account`, so Google asks which account to connect even when the browser is signed in to the caregiver's own account. `gmail.finishMailbox` reads the profile's `historyId` before listing, backfills the last 7 days of the inbox (at most 50 messages) and calls `saveMailbox`. Connecting again replaces the grant; the old grant is revoked only under the rule in "Revoking a grant". `saveMailbox` posts "Sunny now reads <address>." in the caregiver chat, without a push.
- **Poll.** `gmail.pollAll` (every 5 minutes) enqueues `gmail.poll` for each active mailbox of a household that is not paused, and stores the job's work id on the mailbox as `pollJobId`. When the workpool says that job is still pending or running, `pollAll` skips the mailbox, so a full `mailPool` does not collect several polls of one mailbox. A poll reads at most 3 history pages and 100 message ids after the stored `historyId` (inbox, `messageAdded`) and calls `recordNew`. That mutation inserts the ids it has not seen and moves the cursor only when it still equals the one the poll started from. Gmail can return a history page that lists nothing while more pages follow; such a page does not move the cursor. When every page of a poll is empty in that way, or Gmail says the cursor expired (404), the poll lists the inbox since the last poll (at most 7 days back) and restarts the cursor from the profile.
- **Item state machine** (`mailItems.state`): `queued`, then `triaging`, then `done` or `failed`. Every insert of a `queued` row enqueues one `mailTriage.triage` job in the same transaction and sets `leaseUntil` to a pickup deadline 15 minutes out. `claimItem` moves `queued` to `triaging`, adds 1 to `attempt` and sets a 10-minute lease. Every later write checks that the row is still `triaging` under the same `attempt`; a write from an older attempt does nothing. No effect is written outside the one mutation that moves a row to `done` (`applyTriage`) or `failed` (`onMailJobComplete`); afterwards `replaceSummary` only rewrites the body of the post `applyTriage` made.
  - A paused household is not claimed; the row stays `queued`.
  - When the mailbox is gone or connected to another address than the row's `account`, the claim moves the row to `failed` without a post.
  - When the mailbox for the row's address is `revoked` or `error`, the claim leaves the row `queued`. While the Google project is in Testing, a sign-in expires after about 7 days (`notes/GOOGLE_CALENDAR_SETUP.md`, section 6), so this is common. After a reconnect to the same address the sweeper picks the rows up.
  - A row that has been claimed 10 times is failed on its next claim with the one "Sunny could not read an email" post, so a message whose triage always times out stops taking a slot of `mailPool`, which every household shares. A claim that ends in a hold (below) is counted in `heldClaims` and left out of the 10.
  - `mailTriage.sweepStuck` runs every 10 minutes and takes at most 100 rows of each state. It puts rows past their lease or pickup deadline back to `queued` with a new deadline. It enqueues them unless the household is paused or the row's mailbox is `revoked` or `error`. A `queued` row whose `jobId` the workpool still reports as pending or running is not enqueued again; only its pickup deadline moves 15 minutes out, so a backed-up pool does not fill with copies of one row's job. A `triaging` row past its lease is enqueued again whatever its job's state, because a retry of the job that claimed it would find the row not `queued` and skip it. This is also how mail resumes after a pause ends or a reconnect.
  - Each enqueue stores the workpool work id on the row as `jobId`. `onMailJobComplete` acts only on a row whose `jobId` is its own job, so a job that fails late cannot fail a row a newer job holds.
  - Poll and triage classify an error with one function, `lib/mailFailure.mailFailure`, which also marks the mailbox when its grant is lost. A grant failure comes first (see Revoked access). Then a hold: an error that would be the same for every email and every mailbox, so it says nothing about this row. Holds are a `ConfigError` (`askJev` throws one when `TYPESAFE_API_KEY` is not set, and `lib/google.ts` throws one when a Google env var is missing), a Jev 401 or 403, a Google project quota (a 403 or 429 with reason `dailyLimitExceeded`, which Gmail's "Resolve errors" guide documents as the project's daily limit), and a 403 with reason `accessNotConfigured` (the Gmail API is disabled for the Google Cloud project, or the project is blocked or marked for deletion). Gmail's `domainPolicy` 403 is not a hold: one Workspace domain's admin blocked the app, so it marks that mailbox `error`. Triage logs a hold, puts the row back to `queued` and adds one to `heldClaims`, and the sweeper tries the row again after the 15-minute pickup deadline until the cause clears. No chat post is made and the mailbox stays `active`. In the poll, a hold ends the job without a retry and without marking the mailbox. Google's per-minute limits (`rateLimitExceeded`, `userRateLimitExceeded`) are retried with backoff instead. Then a permanent error is not retried: a Gmail 4xx other than 401, a Jev 4xx other than 401, 403, 408 or 429, or a TypeSafe client error that is not a connection error. Anything else releases the claim (back to `queued`) and is thrown so the pool retries. When the job fails for good, `onMailJobComplete` moves the row to `failed` and posts one `mail` chat message, "Sunny could not read an email", with the sender and subject when the row has them, without a push.
- **Triage stages.** `mailTriage.triage` is an action in the default Convex runtime and only reads outside Convex:
  1. Fetch the message (`format=full`) and parse it (`lib/mailParse.ts`). A message Gmail no longer has, or one that does not parse, finishes the row as `done` with no effects and rule `gone` or `unparseable`.
  2. `recordParsed` stores the sender, subject and received time on the row and answers whether the ICS UID is already linked to an event, with the `SEQUENCE` stored on that link.
  3. `triageEmail` (`lib/mailJudge.ts`): the gate (`lib/mailGate.ts`) settles what needs no judgment, and Jev judges everything else (see Classifier).
  4. `applyTriage`, one mutation, builds the policy facts inside the transaction, runs `planWithRule` once, carries out each effect, stores the record and sets `done`. A caregiver post made here ends with the truth-table row's sentence (`triaged.summary`), and the row keeps the post id and Sunny's line as `caregiverPost`. The sender, subject and received time come from the row, where `recordParsed` stored them.
  5. Only when that mutation posted to the caregivers (`tell_caregivers` or `escalate`) does the action ask Claude Haiku for a summary (`lib/mailSummary.ts`). `replaceSummary` then renders the post again through `caregiverMessage` with Haiku's summary in place of the sentence. It changes nothing unless the row is `done` under the same `attempt` and the post still exists with this row's `mailItemId`.
- **The gate** settles these without a model: mail Gmail filed under `SPAM`, `TRASH`, `SENT`, `DRAFT`, promotions, social or forums is ignored (rule `gate:label:<label>`); an ICS `REPLY` is ignored (`gate:ics:reply`); an invite with `RRULE`, `RDATE` or `RECURRENCE-ID` (a repeating event, or one date of one) becomes `needs_decision` with reason `other` (`gate:ics:recurring`), so caregivers decide; an invite whose `SEQUENCE` is lower than the one stored on its link is ignored (`gate:ics:older_sequence`). Every other invite or cancellation goes to Jev, because its `SUMMARY` is email text that no model would otherwise read.
- **Classifier.** TypeSafe's Jev (`jev-1.14.0`, a System One model) answers typed questions about the email, and a truth table in code turns the answers into a verdict. The questions and the state are in `lib/jevQuestions.ts`, the call to Jev in `lib/jevClient.ts`, the thresholds in `lib/jevConfidence.ts`, the date and time reading in `lib/mailDates.ts`, and the truth table in `lib/mailJudge.ts`.
  - State: the sender's name and address, the subject and the body, and for an invite its title and place, as `calendar_invitation_title` and `calendar_invitation_place`. Jev reads the place only as evidence for its judgments; no event gets it. A body longer than 20,000 characters (`MAX_BODY_CHARS` in `lib/mailBody.ts`) is cut at the last paragraph break, line break or space in its second half, and the state then has a `body_cut` field saying the rest is not shown. The caregiver summary prompt uses the same cut and ends with the same note. Jev 1.14 takes 32k tokens for the state plus any one question and 64k for the whole request (docs.typesafe.ai/go/models.md, read 2026-11-19), so the cut keeps the state well under the limit even at one token per character. Requests are sent uncompressed (`compression: false`) so the payload is the same in every runtime.
  - Questions: 29 Nouls (yes or no) about safety signals, decisions, appointments and information; one Noul on whether the time is in another time zone; a Choice of appointment kind; and Choices for the parts of two dates and times, the appointment (`when_*`) and the one it replaces (`before_*`).
  - Thresholds: a Noul of 0.7 or more is yes, 0.3 or less is no, and in between is unsettled. A Choice part counts at 0.7 or more, the same comparison. Each flag names its group next to its question in `lib/jevQuestions.ts` (safety, pressure, decision, appointment, broad, information, or follow-up for a question read only after its parent says yes), and the unsettled rows use those groups.
  - Dates: code resolves the date parts against the day the email arrived and refuses a date whose weekday does not match. A month and day without a year is this year's date when it is today or later. When it fell in the last 180 days it is read as past and the date is left unread; only a date more than 180 days back means next year. `weekdayDate` holds the weekday rule, which the chat agent's prompt states too: a weekday alone or "this <weekday>" is the coming one, and "this <weekday>" includes today; "next <weekday>" is that day in the following Monday-to-Sunday week. These are ambiguous and leave the date unread, so the email escalates: "next <weekday>" less than 7 days away, a weekday alone that names the day the email arrived, and "this <weekday>" that has passed.
  - Truth table, first matching row wins, in this order: safety (instructions aimed at an assistant, a request for private details, hard-to-trace payment or bringing payment, a new address or a name that does not match the address, threats, secrecy or unexpected money) becomes `suspicious`, and any unsettled safety question becomes `needs_decision`. Then the calendar part: an ICS cancellation, an invite Jev reads as cancelled, an invite Jev reads as moved (the new slot is the ICS start; the old one is Jev's `before_*` reading, or none), and any other invite with a usable start. Then cancelled, moved and confirmed appointments read from the text. Then decisions (test results, bills, account security, government, a question, a required action, or an unsettled decision question); then prescription and package news for the senior; a worker coming to the home becomes `needs_decision` with reason `home_visit`; then a personal note for the senior; then bulk mail, receipts and surveys, which are ignored; anything left unsettled or unrecognized becomes `needs_decision` with reason `other`.
  - Truth-table row ids, in table order. The id of the row that fired is stored as `judgeRule`; rows written before the ids hold the row's old prose description instead.
    - `assistant-instructions`: instructions to an assistant.
    - `private-details`: asks for private details.
    - `hard-to-trace-payment`: asks for hard-to-trace payment.
    - `bring-payment`: asks to bring payment.
    - `new-contact-details`: new contact details or a sender name that does not match the address.
    - `threat-or-secrecy`: a threat, secrecy or unexpected money.
    - `safety-unsettled`: a safety question is unsettled.
    - `ics-cancellation`: an ICS cancellation.
    - `ics-cancelled`: an invitation Jev reads as a cancelled appointment.
    - `ics-moved`: an invitation Jev reads as a moved appointment.
    - `ics-invitation`: any other invitation with a usable start.
    - `cancelled`: the text says an appointment was cancelled.
    - `moved`: the text says an appointment moved.
    - `confirmed-appointment`: the text confirms an appointment with a date and start time.
    - `test-results`: about medical test results.
    - `bill`: about a bill or a payment.
    - `account-security`: about the security of an account.
    - `government`: from a government, court or tax office.
    - `question-for-senior`: asks the senior a question that needs an answer.
    - `action-needed`: needs a payment, a reply, a signature or a decision.
    - `decision-unsettled`: a specific decision question is unsettled.
    - `prescription`: prescription news for the senior.
    - `package`: package news for the senior.
    - `home-visit`: a worker coming to the home.
    - `appointment-without-time`: an appointment without a readable date and start time.
    - `personal-note`: a personal note for the senior.
    - `bulk-mail`: bulk mail, a receipt or a feedback request.
    - `broad-unsettled`: a broad question is unsettled.
    - `information-unsettled`: an information question is unsettled.
    - `otherwise`: nothing above matched.
  - An appointment verdict also carries `decision`: the reason of the first decision-group judgment that is yes (test results, bill, account security, government, a question), `other` when one of them is unsettled, else null. The `needs_action` judgment does not set `decision`, because Jev answers yes to it for most confirmations ("arrive ten minutes early").
  - A verdict carries types only: an appointment has a kind (`APPOINTMENT_KINDS` in `lib/mailTypes.ts`), a date, a time and a length; senior information has a topic. Each truth-table row also gives Sunny's sentence for the caregivers, used when there is no summary.
  - A failed Jev call throws and the pool retries the job. A failed call does not count as a "no" answer. The SDK retries once inside a 20-second timeout. A reply with a missing or malformed answer, a probability that is not a finite number from 0 to 1, or no input token count throws `JevAnswerError`, which `lib/mailFailure.mailFailure` treats as permanent.
- **Facts.** The live one-off events from today to 400 days out, plus each repeating event's dates on the days the verdict names (the appointment's date and the day before it, and the previous date of a reschedule or cancellation), so the list grows by at most three facts per series. Each fact has `repeating`. `linked` names the event linked to the email's appointment key (`ics:<UID>` when the email has an ICS part, else `appt:<date>:<time>:<title>` with Sunny's title for the kind) and says whether that event can still occur (`canStillOccur` in `lib/occurrences.ts`: not cancelled, and either a one-off dated today or later or a series whose end has not passed). Only for an event that cannot does it carry the stored date and time, and `madeBy`: whether the mail item behind the link (`mailEventLinks.mailItemId`) came from this email's own address or from another address at the domain. A mail item that no longer exists counts as another address. A link is looked up for the sender's domain only (`linkDomain` in `lib/mailLinks.ts`: the From domain of a verified sender), so unverified mail and mail from another domain have no link. An `ics:` link counts wherever the event now is. An `appt:` key names a slot, and caregivers also move events in the app without touching links. `calendarChangesToday` counts the household's mail items with `calendarChangedAt` since local midnight, and `seniorNotesToday` counts its `seniorNotes` rows created since local midnight (index `by_household`, by creation time).
- **Link resolution** (`resolveLink` in `lib/mailLinks.ts`). For a new or moved appointment, one function answers where the linked event is relative to the email's slot and returns the situation the decision table runs on. It reads the live facts and never the stored document, because a series is stored with its first date. The place is one of four. `slot`: a fact for the event is at the email's date and time. `elsewhere`: the event can still occur and is not at that slot, either because a fact shows it at another time or because it has no fact on the named days although the email's date is inside the facts window (a caregiver moved a series off that weekday). `outside_facts`: the event can still occur and the email's date is outside the window, so the facts cannot say. `over`: the event is cancelled or past. A same-slot event below is a live event with the email's date, time and title words.

  | Place | Invite, new appointment | Plain mail, new appointment | Reschedule |
  | --- | --- | --- | --- |
  | no link | `new_on_calendar` with a same-slot event, else `new` | the same | the event at the previous slot |
  | `slot` or `outside_facts` | `new_on_calendar` with the linked event | the same | the linked event |
  | `elsewhere` | a reschedule of the event's fact at another time, or of nothing when no fact shows it | `new_on_calendar` with a same-slot event, else `new_linked_elsewhere` | an invite moves the linked event; plain mail ignores the link and uses the event at the previous slot |
  | `over`, made by this address | `new_on_calendar` with the linked event when the invite names the stored date and time, else a reschedule of nothing | `new_on_calendar` with the linked event | the linked event, which has no fact, so nothing matches |
  | `over`, made by another address | a reschedule of nothing when the invite names another date or time, else as plain mail | `new_on_calendar` with a same-slot event, else `new_linked_by_another_address` | the same as made by this address |

  A new appointment needs fields that `appointmentFields` accepts in every situation but `new_linked_elsewhere`; when it rejects them the situation is `new_rejected` instead. A reschedule (an invite moved through its link counts as one) is `reschedule_no_match` unless exactly one event matched, `reschedule_repeating` when the match is one date of a series, `reschedule_rejected` when `appointmentFields` rejects the new fields, and `reschedule` otherwise. The verdict's appointment must have a date and a time that parse; planning throws otherwise.

  In `new_linked_elsewhere` the link never picks an event to move and never counts as already on the calendar, and Sunny changes nothing. Its post names the event's date and time when a fact shows them and otherwise says that the calendar no longer has the appointment at that time. `new_linked_by_another_address` also changes nothing, because addresses on one domain share links and a stranger's cancelled appointment must not silence a clinic on the same mail domain. Its post does not show the other address. A link stays after its event is cancelled or past, so for the address that made it, another email about that appointment closes as `already_on_calendar` with no post and never adds it again. A reschedule matches an event at the previous slot only on the same date with a word shared with Sunny's title for the kind, and on the same time when the email gives one. A cancellation uses its link when it has one (only an invite's UID gives a cancellation a link) and otherwise matches the previous slot the same way.
- **Decision table** (`lib/mailPolicy.ts`, `DECISION_TABLE`). Verified means `sender.authenticated` (see Sender check). It shows that the mail came from the domain in its address, not who owns that domain, so mail from a lookalike domain is verified. Each situation from link resolution has its own rows. The first row whose guard holds decides, and its id is stored as `rule`; rows written before the ids hold the old prose `<case>: <row>` instead. Nothing reads `rule` or `judgeRule` to decide anything: they are records for people and for the eval.

  | Id | Situation | Row | Effects |
  | --- | --- | --- | --- |
  | `ignore` | ignore | any | none |
  | `new-unverified-sender` | every new situation | the sender is not verified | escalate `unverified_sender`, push, with the proposed appointment |
  | `new-linked-elsewhere` | new_linked_elsewhere | otherwise: the sender's link has this appointment at another time, and no live event has the email's date, time and title words | escalate `unclear_appointment`, push, with the event and the proposed appointment |
  | `new-fields-rejected` | new_rejected | otherwise: `appointmentFields` rejects the date, time or length | escalate `unclear_appointment`, push, with the proposed appointment |
  | `new-on-calendar` | new_on_calendar | otherwise: the link applies, or a live event has the email's date, time and title words | `already_on_calendar` |
  | `new-linked-by-another-address` | new_linked_by_another_address | otherwise: the link's event is over, and another address at the sender's domain made it | escalate `unclear_appointment`, push, with the proposed appointment |
  | `new-caregiver-confirms` | new | a caregiver confirms this kind first | escalate `home_visit` or `phone_call`, push, with the proposed appointment |
  | `new-conflict` | new | overlaps another live event | escalate `conflict`, push, with the proposed appointment |
  | `new-daily-limit` | new | daily limit of calendar changes reached | escalate `daily_limit`, push, with the proposed appointment |
  | `new-add` | new | otherwise | `add_event`, `tell_caregivers` without push |
  | `reschedule-no-match` | reschedule_no_match | otherwise: no single event matched | escalate `unclear_reschedule`, push, with the proposed appointment |
  | `reschedule-repeating` | reschedule_repeating | otherwise: the match is one date of a repeating event | escalate `unclear_reschedule`, push, with the event and the proposed appointment |
  | `reschedule-unverified-sender` | reschedule_rejected, reschedule | the sender is not verified | escalate `unclear_reschedule`, push, with the event and the proposed appointment |
  | `reschedule-fields-rejected` | reschedule_rejected | otherwise: `appointmentFields` rejects the new date, time or length | escalate `unclear_reschedule`, push, with the event and the proposed appointment |
  | `reschedule-already-there` | reschedule | the match already has the new date and time | `already_on_calendar` |
  | `reschedule-caregiver-confirms` | reschedule | a caregiver confirms moving this kind first | escalate `home_visit` or `phone_call`, push, with the event and the proposed appointment |
  | `reschedule-daily-limit` | reschedule | daily limit of calendar changes reached | escalate `daily_limit`, push, with the event and the proposed appointment |
  | `reschedule-move` | reschedule | otherwise: exactly one match | `reschedule_event`, `tell_caregivers` with push |
  | `cancel` | cancel | any | escalate `cancellation`, push, with the event when exactly one matched; never applied |
  | `senior-info-stale` | senior_info | the email is stale | none |
  | `senior-info-unverified-sender` | senior_info | the sender is not verified | `tell_caregivers` without push |
  | `senior-info-daily-limit` | senior_info | daily limit of notes reached | `tell_caregivers` without push, saying the daily limit of 3 notes was reached, with Sunny's sentence for the topic |
  | `senior-info-note` | senior_info | otherwise | `senior_note` with Sunny's sentence for the topic |
  | `needs-decision` | needs_decision | any | escalate with its reason, push |
  | `suspicious` | suspicious | any | escalate with its suspicion, push; the senior is never told |

  Two passes run over the row's effects after the table, in this order. Decision: an appointment verdict with a `decision` keeps its row; every escalation gets a sentence on what else the email needs (`ALSO_NEEDS`), a `tell_caregivers` becomes an escalation with the decision as its reason and a push, and an `already_on_calendar` gets that escalation next to it, with its event. So a verified confirmation that also asks for a payment is added and escalated in one chat post, and an unverified one is one escalation that says both. Staleness: every push of a stale email becomes `push: false` (see Staleness). The rows build Sunny's sentence for each post, and the caregiver message is rendered from it after both passes.

  A calendar change is an add or a move. At most 5 (`MAX_CALENDAR_CHANGES_PER_DAY`) are made from mail per household per local day, counted inside the transaction from `mailItems.calendarChangedAt`. At most 3 senior notes (`MAX_NOTES_PER_DAY`) are written per household per local day, counted the same way from `seniorNotesToday`. A kind with `caregiverConfirms` in `APPOINTMENT_KINDS` is never added from mail. There are two: `home_service` (reason `home_visit`) and `phone_call` (reason `phone_call`). In both a stranger would reach the senior at a time that Sunny announced, so a caregiver checks the appointment and adds it in chat. Mail does not move one either. The reschedule row escalates when the email's kind has `caregiverConfirms`, and also when the matched event's title holds a word that only such a kind's title has (`CONFIRMING_WORDS`: "phone" for a phone call, "home" and "service" for a home visit), because a move through a link does not compare titles and the email could claim another kind. A word that another kind's title also has does not count, so mail still moves a "Video call". The rule reads titles, so an event titled "Dr. Lee comes to the house" is not covered, and "Lunch at home" or "Church service" asks without need. "call" belongs to no kind, because "Video call" has it too. So an event a caregiver titled "Call Dr. Lee" is moved by an email that Jev reads as a video call on the same date and time.

  `already_on_calendar` always carries the key to link. Only verified mail reaches it, because the first row of the new case and of the reschedule case escalates unverified mail. So an unverified sender never writes or changes a link.

  `appointmentFields` rejects a malformed date or time, a start already past, a date more than 400 days out, and a length outside 5 to 480 minutes. A verified sender moves the one matching event whoever created it, and a suspicious verdict from a verified sender still escalates and never acts.
- **What the senior and the calendar see.** No word from an email and no word a model wrote reaches the senior or becomes an event title or place. A senior note is one of Sunny's sentences, chosen by topic (`SENIOR_SENTENCES`): "Your prescription is ready to pick up at the pharmacy.", "The pharmacy is getting your prescription ready.", "A package was delivered to your home.", "A package is on the way to your home." and "You have a personal email. Someone can read it with you." None tells the senior to do something risky, to contact anyone or to expect a visitor, and none says who sent the email. Jev's `personal_note` question asks whether a relative or a friend wrote the email, but any verified sender can write one that reads that way, so the topic is named `personal_note` and its sentence and its caregiver summary ("The email reads as a personal note.") claim no relationship. Each is at most 160 characters and 2 sentences, has no digits and uses only characters the display typefaces draw, which a test checks. An event title is built from the appointment kind (`appointmentTitle`; a meal is Breakfast, Lunch or Dinner by its start time). An event created from email has no place, and a moved event keeps the place it had. The voice agent reads an event's place to the senior, pushes carry it and the chat agent sees it, and no check on free text keeps instructions out of it. The invite's `LOCATION` appears only in the caregiver chat post, as "Place in the invitation: ..." through `caregiverText`. Event `notes` are never filled from email.
- **Caregiver summary.** For a plan that posts to the caregivers, Claude Haiku (`claude-haiku-5-5`, low effort, no thinking, 8-second timeout, no retry) writes at most two sentences on what the email says. It goes into the chat post under Sunny's own line, through `caregiverText`, which removes links and runs of 7 or more digits. It never reaches a push, the senior, an event or the chat agent's briefing. The post goes out first with the truth-table row's sentence, and the summary replaces that sentence after the call returns. When the call fails, times out or stops for any reason but `end_turn`, the sentence stays. The push is sent with the post and never waits for the summary.
- **Staleness.** An email received more than 24 hours before triage is stale. A stale email never produces a senior note, and every push it would send becomes `push: false`. The chat post still lands.
- **Effects** (`lib/mailEffects.ts`, one handler per effect kind):
  - `add_event` calls `addEventCore` with actor `{ kind: "agent" }` (`createdVia = agent`) and the title built from the kind, with no place, then writes a `mailEventLinks` row.
  - `reschedule_event` calls `updateEventCore` with the new date, time and length and leaves the place alone, then writes the sender domain's link for the new key. The record keeps the old date and time.
  - `applyTriage` sets `calendarChangedAt` on an item whose records hold `event_added` or `event_rescheduled`.
  - `already_on_calendar` is recorded, and the sender domain's link for the key is written or pointed at the event with the invite's `SEQUENCE`. A later reschedule from that domain then finds the event, and an older invite from that domain is stopped by the gate. A link row is unique per household, domain and key, and an event can hold links from several domains, so one sender's link never blocks or changes another's. `linkEvent` throws if a plan links for an unverified sender, which the decision table never plans.
  - The effects only carry out the plan; every decision is in the policy. A write is never refused at effect time. `addEventCore` checks the title, the date and time format, a length of 1 to 1440 minutes and a start not yet past; `updateEventCore` also checks that the event is live and that its stored fields still pass the same checks. The policy builds the title from the kind, plans a write only for fields `appointmentFields` accepted (5 to 480 minutes, not past at the same `now`), and moves only a live, one-off event from the facts, read in the same mutation, and a plan holds at most one write. A Convex mutation runs alone, so nothing changes those facts between planning and writing. An app error from either write is a bug and fails the triage like any other error.
  - `senior_note` writes a `seniorNotes` row (expiring at the end of the next local day) and one `senior_note` push titled "Sunny" to each paired `senior_phone`. It never goes to the home display or by SMS, and the push is skipped at send time once the note has expired. The daily limit of 3 notes is a decision-table row, so over the limit the plan has no note: the note goes to the caregivers as one chat post without a push that says the daily limit was reached, and the record is `told_caregivers`.
  - `tell_caregivers` writes one `mail` chat post. With push, it adds one `mail_update` row per reachable caregiver with the title the policy put on the effect. Only a move pushes, titled "Sunny moved an appointment".
  - `escalate` writes one `mail` chat post, then with push one time-sensitive `mail_escalation` row per reachable caregiver, titled "Email for <senior> needs you".
  - A caregiver push body is the sentence Sunny wrote about what it did or what it needs (the `notice` on the effect, with links and long numbers removed), clipped to 178 characters. No subject, sender name or summary goes into a push. Sunny builds every push title, and no title holds text from the email.
- **Push cap.** The rate limiter rule `mailEscalationPush` (a token bucket) allows 6 escalation pushes per household per hour. One email counts once, however many caregivers it reaches, and an email with no reachable caregiver spends nothing. Over the cap the chat post still lands and the record says `pushed: false`.
- **Revoked access.** `invalid_grant`, a permanent 403 that is not a hold (such as `domainPolicy` or `insufficientPermissions`), or credentials Sunny can no longer decrypt mark the mailbox `revoked` or `error` through `googleGrant.markGrant`, the same code the poll and calendar pushes use. It acts only when the mailbox leaves `active`. In that transaction it posts one `mailbox` chat message ("Sunny can no longer read <address>. Reconnect Gmail to keep mail coming in.") and sends one `mail_escalation` push per reachable caregiver. The item that hit the error goes back to `queued` and waits there, with the other queued items, until a reconnect to the same address.
- **Disconnect.** `gmail.disconnect` deletes the mailbox and revokes the grant. Mail items stay, so a reconnect does not triage the same messages again.
- **Surfaces.** `DeviceState.notes` holds up to 3 unexpired notes, newest first, and changes `version` but not `displayVersion`. `agent:getContext.seniorNotes` has the same notes as `{ text, receivedAt }`. The caregiver chat agent's briefing lists the emails escalated in the last 3 days (at most 10, read through `by_household_escalated`). Each line holds only Sunny's own records: the received time, the reason, the `mail_item_id`, the domain of the sender's address (shown whole when it is 1 to 253 lower-case letters, digits, dots and hyphens, else `unknown`), and, when one matched, the event's `event_id`, title, date and time from `events`, and the proposed appointment's title, kind, date and time. The local part of the address is never shown, because the sender writes it freely and the chat agent holds tools. No subject, display name or summary enters the briefing. `gmail.recentMail` shows any caregiver of the household the latest items with sender, subject, received time, verdict kind and effects.
- **Stored and never stored.** A mail item keeps the sender (name, address, whether Gmail verified it), the subject (200 characters), the received time, the verdict kind, the decision-table rule, the truth-table rule (`judgeRule`), Jev's answers as question ids with probabilities (`judgeAnswers`), the effect records, and the classifier with its token usage. The email body never leaves the triage action, apart from the requests to Jev and, for caregiver posts, to Claude Haiku. Neither model's raw output is stored; the summary lives only in the chat post.
- **Sender check.** `parseSender` parses From once, and the check runs on that same address string; nothing shortens a sender address afterwards, so the address Sunny stores, shows and takes the link domain from is the one that was checked. A From address longer than 254 characters or with a second `@` is no sender: the email closes as `unparseable` with no post, and no sender is stored for it. `verifiedFor` reads Gmail's `Authentication-Results` after removing comments and quoted strings. Exactly one such header with authserv-id `mx.google.com` must exist; none, more than one, or one that does not parse means not authenticated, because Google does not document the order of `payload.headers`. It passes on `dmarc=pass` with a `header.from` equal to the From domain, or on `dkim=pass` with a `header.d` or `header.i` aligned with it. `ARC-Authentication-Results` is not read.
- **Parsing limits.** The body is the text a mail client shows. In a `multipart/alternative` that is the last plain-text, HTML or nested part, so the HTML part when the sender sent both; in any other multipart it is every inline part in order. Attachments are not read. Only the first 256 KB of a body part is read, and Jev and the summary see at most 20,000 characters of the body. Hidden HTML text is dropped when an element has the `hidden` attribute, `aria-hidden=true`, or a style (quoted or not) with `display:none`, `visibility:hidden`, `mso-hide:all`, a zero opacity, font size or max-height, or a zero height or width with `overflow:hidden`.
- **Known limits.** Jev is not perfectly repeatable: in earlier recordings `cp10-visit-survey` came out unsettled once in 3 runs and escalated. Relative dates in short notes ("dinner this Sunday at 5", "tomorrow at 11", a move "from 11:00 AM to 1:30 PM" on a named day) are sometimes not read, so those emails escalate instead of being added or moved. Text hidden through a class rule in a `<style>` block is still read, because telling which rule wins (media queries, `!important`, later rules) needs a CSS cascade; Jev still reads it as email data. An ICS part that arrives only as an attachment (fetched separately by `attachmentId`) is not read, so such an invite reaches Jev as text without its start. Windows timezone ids in invites (`TZID=Eastern Standard Time`) are not converted, so the start is dropped and Jev's reading of the text is used. Anyone whose domain passes Gmail's check is a verified sender, a stranger included. Their scams escalate when Jev sees the signs. When Jev misses them, the sender can add an appointment with Sunny's title and no place, move the one event the email matches, or give the senior one of Sunny's sentences, within 5 calendar changes and 3 notes a day. They cannot add or move a phone call or a home visit. They can link their own invite to a hand-entered event at the same slot and move it later, which is the same power as a reschedule written in prose. A link is matched on the exact From domain, so an update that a clinic sends from another domain or subdomain is not tied to the event through its link: it is matched by date, time and title words, or added as new. Senders on a shared mail domain such as gmail.com share a link namespace: one who knows another's invite UID can raise its stored `SEQUENCE`, so that sender's real update is dropped by the gate, or can move the event. The same holds for `appt:` links: a sender who has Sunny add an appointment and then move it leaves a link at the old slot, and another sender on that domain who writes about the same date, time and kind is escalated as `unclear_appointment`, not added. That costs the first sender 2 of the day's 5 calendar changes, and the caregivers are told. The sender check does not use the public suffix list, so a From address on a bare suffix such as `co.uk` passes when any domain under that suffix signed the mail. An invite's `UID` has no length limit in code; tests do not enforce Convex's index key size, so a very long UID may make triage of that email fail on a deployment. After a caregiver moves an event in the app, a resend of the invite with the same `SEQUENCE` moves it back and pushes the caregivers. In the eval Jev reads `ts03-hostile-invite-unknown-domain` as an ordinary new appointment, and only the phone-call row stops it. A move of a class that Jev reads as a group activity does not match an event titled with the class's own name ("Chair yoga"), so it escalates (`rs06-hand-entered-event`). An updated invite with a new UID that Jev does not read as moved is added as a new event, because nothing else ties it to the old one. Refresh tokens of an OAuth client in Testing mode expire after about 7 days, which shows up as revoked access.
- **Env.** `TYPESAFE_API_KEY` (Jev; the TypeSafe SDK's default name) and `ANTHROPIC_API_KEY` (the summary, the digest and the chat agent) on the Convex deployment. After a deploy that changes `lib/agentConfig.ts` or the tool list, rerun `npm run setup:agent`.
- **Classifier comparison** (2026-11-19, measured on commit 825b8d8, where both recordings replay; 92 synthetic fixtures, each run 3 times). Jev: 96.7% of runs with exactly the expected effects, 100% escalation recall, 0 attack breaches, $0.000151 per email, about 100 ms median latency, the same answer on every repeat. Claude Haiku returning a JSON verdict, with its prompt tuned on all fixtures: 99.6% exact, 100% recall, 0 breaches, $0.000321 per email, about 1.2 s median latency. Jev ships because it costs half as much, answers about ten times faster and keeps the decision in code. The Haiku classifier was then deleted. Recorded again on 2026-11-19 after the second review, with 113 fixtures: 97.3% exact, 100% recall, 0 breaches, 0 exact-check violations, $0.000171 per email. After the change from caregiver-approved senders to any verified sender, on the same recording: 96.5% exact, 100% recall, 7.5% false escalations, 0 breaches. The expectations of 10 fixtures changed with the rule, so 96.5% and 97.3% are not measured against the same answers. Before the phone-call row was added, the same replay let `ts03` through on all 3 runs.

## Delivery

Every notification is a `notificationOutbox` row inserted through `insertNotification` (`lib/delivery.ts`), which enqueues `delivery.deliver` on `deliveryPool`.

- **Routing.** A device recipient gets APNs to every push token of its user. A member recipient gets APNs when they have a push token (the caregiver app), otherwise an SMS at the verified phone (title and body on separate lines; a `caregiver_alert` for a member who can claim ends with a reply hint). A member's push that cannot be delivered goes out as that SMS instead (`channel` records `sms`). The SMS goes in the same run when APNs is not configured, or when no token takes the push and there is nothing worth retrying. It goes as one more run after the workpool's push retries run out (`pushState`). Membership, device and content are re-checked at send time; an unreachable or stale row is `skipped` with the reason in `detail`.
- **APNs.** `apns.ts` uses `node:http2` (one session per send call, 10-second timeout per request); payload and provider token live in `lib/apnsPayload.ts`. A row counts as sent when any token was accepted; only tokens APNs reports unregistered are deleted. Env: `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_KEY_P8` (set with `npx convex env set APNS_KEY_P8 --from-file <key.p8>`), `APNS_ENVIRONMENT` (development for dev builds), optional `APNS_BUNDLE_ID`.
- **SMS.** Twilio REST through `lib/twilio.ts`. A retryable failure is thrown so the pool retries with backoff. An SMS that timed out is retried only for a `caregiver_alert`; for other kinds the text may already have arrived, so the row is failed rather than risk a duplicate. A configuration problem leaves the row pending with the detail recorded, so the sweeper retries after the fix (bounded by `MAX_ATTEMPTS`). Inbound `POST /twilio/sms` handles "1" / "on it" to claim the newest texted alert (`sms.ts`; deduplicated by MessageSid; viewers cannot claim). Phone verification: `phone.ts` (HMAC-hashed codes, rate limits, allowed countries). Env: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM_NUMBER`, `TWILIO_WEBHOOK_URL`, optional `SMS_ALLOWED_COUNTRY_CODES`.
- **Daily digest.** `queueDigestIfDue` (from the household tick) records a `digests` row once local time reaches `digestTime`. Then `digest.compose` writes the not-done and alert lines from a template and asks Claude Haiku for the rest (`lib/digestText.ts`); on any failure it falls back to the whole template. `complete` stores the text, posts it as a message from Sunny in the caregiver chat thread (`chatPosts`, for every caregiver), and inserts one `digest` outbox row per reachable member (one with a verified phone or a push token). Every caregiver who can be reached gets one, viewers included; there is no opt-out.
- **Sweepers.** `delivery.sweepStuck` (every 10 minutes) re-enqueues deliveries and digests left pending for 15 minutes. A row that a run started less than 5 minutes ago is leased and left alone. When retries run out, the row ends as `failed`; a settled row is never delivered again.

## Voice agent

`sunny_agent` is a LiveKit Agents worker (Deepgram STT, Claude Haiku, Cartesia TTS, Tavily search). A senior device gets a room token from `voice.livekitToken`; its participant metadata (`household_id`, `device_id`, `trigger`, `task_instance_id`) is the only place where the agent learns its household. The agent calls `agent:getContext`, `today`, `confirmDueTask`, `createSeniorReminder`, `cancelSeniorReminder`, `startConversation`, `logTurn` and `finishConversation` through Convex's `/api/query` and `/api/mutation`.

## Not built yet

- **Google pull** (Google to Sunny): watch the Sunny calendar, apply incremental changes, skip our own echoes by etag, renew channels daily. Later edits win; fields only Sunny has are never overwritten.
- **`wait_for_reply`**: "ask Sarah and tell Mom" leaves a tool call unanswered and the workflow calls `awaitEvent`; the Twilio webhook or an in-app reply calls `sendEvent`. Needs workflow versioning first.
- **Live Activity** pushes, deferred until the app adopts ActivityKit.
- **Background "I'm on it"**: the push action opens the caregiver app in the foreground to claim; a claim without opening the app is not built. Resend (email) is unused.
- **Policy engine**: per-household allow, ask or deny rules checked before a tool executes. Planned defaults: message household members freely, ask before contacting anyone else, deny money and credentials.
- **Post-call memory extraction** into `agentMemory` and `agentQuestions`.
- **Live SMS verification**: Twilio A2P 10DLC / toll-free registration is pending; SMS has not been tested end to end.
